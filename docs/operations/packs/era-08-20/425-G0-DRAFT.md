## 0. Что такое G-кампания (контекст)
G — автоматизированная latency/перф-валидация движка: unattended-раннер гоняет сборку в Chrome headless, снимает метрики (latencyHint/baseLatency/RTL/load-to-first-audio/stretch-узлы), отправляет на эндпоинт, строит корреляцию с конфигами (env-fingerprint). G0 — пилотный прогон на одном конфиге для проверки обвязки. G0.5 — доработка обвязки до полноценного прогона. G1 — первый полный baseline (числа для порогов). G3 — этап классификации исходов.

## 1. Цель G0 (пилот)
- Проверить **обвязку целиком**: раннер → прогон → сбор метрик → эндпоинт → envelope → отчёт. Один конфиг, один билд, одна платформа.
- Калибровать пороги и правила классификации на реальных данных.
- Выход: **решённый вопрос «раннер работает end-to-end»** + 1 эталонный прогон для G1.

## 2. Env-FINGERPRINT (обязательные поля, по Ц3)
```
fingerprint = {
  latencyHint,          // из audioContext.ts (C14: 'interactive'; флип = НОВАЯ G-кампания)
  baseLatency,          // AudioContext.baseLatency (замер, сек)
  rate,                 // 44100 | 48000 (реестр F5, rate-колонка)
  sha,                  // git SHA сборки (C16-C24)
  chrome,               // версия Chrome (headless через WSL: /mnt/c/.../chrome.exe)
  os,                   // Windows host (WSL-драйв)
  hardware,             // CPU/GPU (navigator.hardwareConcurrency + UA)
  v3Engine,             // VITE_ENGINE ('v2' | 'v3') — в fingerprint ОБЯЗАТЕЛЬНО
  micDeviceId,          // 'default' | точный (deviceId из localStorage) — влияет на RTL
  audioOutputDevice,    // monitor:deviceId — влияет на RTL
}
```
**Правило Ц3:** любой флип fingerprint-поля (кроме chrome/os/hardware) = **новая G-кампания**. Реестр хранит историю кампаний.

## 3. ЭНДПОИНТ E/X и ПЯТЫЙ ИСХОД (G3)
- **E-эндпоинт** — сбор метрик (обязательная отправка каждого прогона).
- **X-эндпоинт** — публикация итогового вердикта/агрегата; вердикт не двигает, только характеризация.
- **Пятый исход в G3** (добавить к 4 базовым: passed/failed/infra-error/config-drift): **`bounded out-of-envelope closure`** — X-коллапсы при чистых E → позитивное закрытие прогона с зафиксированной задокументированной границей (например: единичный прогон без повторов, аудио-поток не подтверждён, мик-устройство отсутствовало). Это НЕ исторический ярлык H14 (состояние «не смогли определить», зовущее переоткрыть критерии) — такой ярлык в G-документах не используется нигде; инфра-аборты классифицируются отдельно как infra-error.**
  - Правило: bounded closure НЕ считается тест-результатом, НЕ ломает регрессию, но требует повторного прогона ТОЛЬКО при наличии X-коллапса (закрытие «вовне»); при чистых E без X — это полноценный passed.

## 4. БЮДЖЕТ (по Ц3)
- **112 учтённых** прогонов (разрешённый объём данных),
- **120 кап** (жёсткий потолок),
- **≤8 ретраев** (перезапуски на infra-error/таймаут),
- **таймбокс** на кампанию,
- **правило эскалации:** при превышении бюджета/таймбокса или появлении систематической infra-error → остановка + отчёт Ц3, НЕ авто-продолжение.

## 5. ИНФРА-ОШИБКА ≠ ТЕСТ-РЕЗУЛЬТАТ
- Отдельная классификация: infrastructure-error (chrome crash, WASM-init fail, IDB unavailable, endpooint unreachable) — **никогда не считается провалом теста**.
- Обязательная **корреляция с конфигами**: если infra-error воспроизводится только на одном конфиге — это сигнал конфиг-дрейфа (config-drift), а не инфраструктурный шум.
- Учёт инфра-ошибок в отчёте отдельным блоком.

## 6. ENVELOPE-ДОК (границы измерения)
Источник истины — **фактический код, не теория:**
- **Граф измерения:** `HybridPipelineService` (Phase F: 7×StretchInstance WASM, PipelineController, RouteCheck, RECON-SEEK, _stretchMeters) — что именно замеряется и где: вход (programInput/vocalHallInput) → стемы → монитор-шина (MonitorRouter) → устройство вывода.
- **UI-границы:** измерение/валидация только в рамках страницы (TakesPanel/Quest/Visual-карточки); фоновые вкладки исключаются (rAF-деградация — документально).
- **Известные асимметрии:** V3StatePublisher (50мс кэш), throttled-rAF в фоне (до 250мс), MediaRecorder cold init (4.8с из C23) — все учитываются в модели измерения.
- Плюс: метрика M2-latency (load-to-first-audio, main.tsx:283) и RTL (реестр §H — цифра после бандла).

### 7a. WARMUP-ПРАВИЛО (урок сессии 24.08, эмпирика)
**Раннер НЕ сэмплирует метры сразу после старта транспорта.** Первые секунды прогона = warmup; измерения — после разгона, минимум **2 замера с паузой ≥1.5с** (наблюдение: ложно-нулевой снимок сразу после рестарта, валидный на +1.5с). Иначе harness наложит ложный коллапс на каждый прогон — ровно тот класс ошибки, от которого защищает пререгистрация.

**G4-калибровочная точка (для watchdog-спеки):** эмпирически наблюдалось ~1.5с до валидных показаний метеров после play/seek. `T_quiesce=500мс` может быть маргинален против этого. **Число НЕ меняем** (одно наблюдение, синтетический трек) — точка записывается как вход калибровки G2-baseline. Страховка остаётся: требование «устойчиво ≥ T_sus» — одиночный нулевой кадр не подозрение.

## 9. G0.5 (следующая итерация после G0-ревью)
- `.mjs`-обвязка (см. §7) — реализация.
- **Провенанс vs upstream:** каждый прогон фиксирует источник данных (SHA, конфиг, окружение) — аудируемость.
- **upstream-issues:** фиксация проблем движка/браузера, найденных в прогонах, отдельным списком.
- **Механизм-гипотезы → матрица этапа A:** каждая гипотеза о механизме задержки (например, «WASM-stretch добавляет X мс», «latencyHint меняет baseLatency на Y») получает строку в матрице: гипотеза → измерение → подтверждено/опровергнуто → действие.
