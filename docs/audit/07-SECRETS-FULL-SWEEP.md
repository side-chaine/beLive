### Почему это хуже MVSEP

MVSEP-ключ = можно слить бесплатную квоту. Досадно, не более.

**Токен бота = полный контроль над ботом.** Тот, кто его нашёл, может:
- читать **все сообщения**, которые приходят боту;
- писать **от имени бота** в любые чаты, где он есть;
- подменить webhook и перехватывать всё дальше;
- удалить бота.

Ключ к квоте — это деньги. Токен бота — это личность.

Оба лежат в `.env` (в gitignore — в git не попали, это плюс).

**Но:** они объявлены как `VITE_*`, а **Vite встраивает каждую `VITE_*` переменную

Это не «потенциальная уязвимость» (как было с MVSEP) — это **реализованная утечка.**

Не «украдут аккаунт» — кража **квоты**. Ключи привязаны к твоему аккаунту, лимиты
сгорят, метаданные перестанут подтягиваться. Плюс Last.fm может забанить аккаунт
за нарушение ToS (ключи не предназначены для публикации).

Проблема **не в файле**, а в том, что ключи уезжают в бандл.

Добавил пояснения + маркеры `secret-ok` в четырёх местах использования

## 4. Системная причина: префикс `VITE_`

Четыре секрета за один день — это не «четыре ошибки», это **одна ошибка,
повторённая четыре раза**.

> **Секрет с префиксом `VITE_` — это не секрет, а публикация.**
>
> Vite подставляет значения переменных **текстом на этапе сборки**. Он не
> анализирует, достижим ли код, и не спрашивает, публичный ли ключ.

Проверено на MVSEP: ветка с ключом была физически недостижима (условие всегда
истинно) — и Vite всё равно подготовил бы значение к встраиванию.

**Правило, вступающее в силу сегодня:**

| Префикс | Что можно | Примеры |
|---|---|---|
| `VITE_*` | **только публичные конфиги** | URL воркера, ID, флаги режима |
| без префикса | секреты | `wrangler secret put` → `env.*` внутри Worker |

## 5. Новый гейт: `scripts/check-secrets.mjs`

Три правила, каждое на своей области:

| Правило | Область | Ловит |
|---|---|---|
| **R1** | код + конфиги | `VITE_*` переменная с «секретным» именем — даже без значения |
| **R2** | любые текстовые файлы | известные форматы: Google `AIza…`, OpenAI `sk-…`, GitHub `ghp_…`, Slack `xox…`, AWS `AKIA…`, PEM, URI БД с паролем |
| **R3** | любые текстовые файлы | `SECRET_NAME = значение`, если значение похоже на настоящий ключ, а не на плейсхолдер |

**Режимы:**
```bash
node scripts/check-secrets.mjs            # только отслеживаемое = ГЕЙТ КОМИТА
node scripts/check-secrets.mjs --staged   # только то, что сейчас коммитится
node scripts/check-secrets.mjs --all      # + gitignored (.env, *.pem) = АУДИТ
node scripts/check-secrets.mjs --install-hook
```

**Сделано:**
- ✅ **Pre-commit хук установлен** — коммит с секретом теперь невозможен
- ✅ Гейт на отслеживаемых файлах — **зелёный** (869 файлов, 0 находок)
- ✅ `--all` — красный на `.env` (это находки №2 и №3, ждут ротации)

### Почему гейт зелёный, а ключи в `.env` остались

Гейт проверяет **то, что уезжает в репо**. Локальный `.env` в gitignore — его
содержимое в репо не попадает, это нормальное место для ключей разработчика.
Полный аудит (`--all`) их видит и репортит — это ровно то разделение, которое
нужно: гейт не орёт на каждого разработчика, аудит не пропускает ничего.

### Подавление: `secret-ok` и `secret-ok-next-line`

Гейт, который всегда красный, обходят через `--no-verify`. Поэтому известные и
принятые находки можно подавить — но **каждое подавление видимо, ищется grep'ом
и содержит причину**:

```ts
// secret-ok-next-line: public client-side key by provider design.
const KEY = import.meta.env.VITE_LASTFM_API_KEY || '';
```

Найти все подавления: `grep -rn "secret-ok" . --exclude-dir=node_modules`

### ⚠️ Известная слабина

GitHub Secret Scanning **уже должен был** прислать алерты по токену бота — они
приходят владельцу репо. Проверь почту и вкладку Security → Secret scanning
alerts: возможно, алерты висят с июня непрочитанными.

Когда всё уляжется — можно вычистить историю косметически. Скажи, если нужно.

Твой локальный `dist` и dev-режим на них завязаны. Удаление без ротации = сломанная
разработка и всё те же скомпрометированные ключи. Сначала новые ключи — потом
замена.
