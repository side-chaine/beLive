# ADR-0010 · Целостность среды разработки: `node_modules` не синхронизируется, только устанавливается

**Статус:** proposed · **Дата:** 2026-08-29 · **Волна:** W−1 (блокирующая, перед всеми остальными)
**Связано:** [01-BASELINE §1](./01-BASELINE.md), [ADR-0011](./ADR-0011-git-and-doc-visibility-policy.md), [TEAM-007 §R1](../../team-m/REGISTRY.md)

---

## Контекст

На машине Windows (`win32/x64`) проект **не собирается и не тестируется**. Это не гипотеза, а замер (см. [01-BASELINE §1](./01-BASELINE.md)):

| Команда | Результат |
|---|---|
| `npm run typecheck` | ❌ `tsc` не является командой |
| `npm run lint` | ❌ `eslint` не является командой |
| `npm run build` | ❌ `MODULE_NOT_FOUND` — `@rollup/rollup-win32-x64-msvc` |
| `npm run test` | ❌ `Cannot find module './rolldown-binding.win32-x64-msvc.node'` |
| `npm run verify:ci` | ✅ работает (идёт через `npx`, в обход `.bin`) |

**Диагноз.** `node_modules` содержит **только Linux-бинари**:

```
@rolldown/binding-linux-x64-gnu/rolldown-binding.linux-x64-gnu.node
@rolldown/binding-linux-x64-musl/…
@rollup/rollup-linux-x64-gnu/rollup.linux-x64-gnu.node
@rollup/rollup-linux-x64-musl/…
lightningcss-linux-x64-gnu/…
lightningcss-linux-x64-musl/…
@esbuild/linux-x64/
```

При этом `package-lock.json` **корректен**: в нём есть `@rolldown/binding-win32-x64-msvc@1.0.1` с `os: ["win32"], cpu: ["x64"]`. npm, запущенный на Windows, **не может** установить `linux-x64`-бинарь. Следовательно `node_modules` не устанавливался здесь — он **приехал готовым** через OneDrive с Linux-машины.

**Второе следствие.** `node_modules/.bin` содержит 32 Unix-шимa и **ни одного `.cmd`/`.ps1`**:

```
$ head -c 60 node_modules/.bin/tsc
#!/usr/bin/env node
$ ls node_modules/.bin/*.cmd | wc -l  →  0
```

Windows-npm не может выполнить ни один npm-скрипт, вызывающий инструмент.

**Почему это блокер, а не «неудобство».** Вся программа модернизации строится на гейтах: «ноль ошибок tsc», «тесты зелёные», «лиnt чистый». Ни один из этих гейтов **не может быть проверен локально**. Гейт, который нельзя прогнать на своей машине, не будет соблюдаться — не из вредности, а потому что иного способа работать нет.

Это объясняет главную загадку проекта: как 307 ошибок компилятора могли жить при `strict: true`. Ответ — **никто не мог их увидеть**.

---

## Решение

Три правила, применяемые вместе.

### 1. `node_modules` исключается из синхронизации — навсегда

Рабочая копия **выносится из OneDrive** (это кроссплатформенный риск R1, он шире данной проблемы). Для текущей копии — немедленно исключить `node_modules` из синхронизации (в OneDrive: «Всегда хранить на этом устройстве» не помогает; нужен выбор папок синхронизации либо `.gitignore`-подобный механизм облака).

### 2. Установка — только нативной командой на целевой машине

```bash
# Windows (PowerShell / Git Bash) — на машине, где будем работать
rm -rf node_modules          # удаляем приехавший Linux-мусор
npm ci                       # ставит win32-бинари и .cmd-шимы
```

Проверка успеха — исполняемость шимов:
```bash
ls node_modules/.bin/*.cmd | wc -l   # должно быть > 0
ls node_modules/@rolldown/            # должен быть binding-win32-x64-msvc, не linux
```

### 3. Волшебный пендаль в CI: проверка чистоты платформы

Добавить в CI шаг, который ловит ситуацию, если она повторится:

```yaml
- name: Verify native toolchain matches runner
  run: node scripts/check-native-bindings.mjs
```

Скрипт читает `process.platform`/`process.arch` и проверяет, что для каждого нативного пакета из `package-lock.json` (с `os`/`cpu`) в `node_modules` присутствует **правильная** платформенная сборка, а чужих нет. Красный свет означает: кто-то принёс `node_modules` с другой ОС.

### 4. `.gitignore` — страховка от повторения

```gitignore
node_modules/
!.gitkeep
```
(уже есть) плюс явная фиксация в `TEAM-007-ENGINEERING-PROCESS.md`: **переносить `node_modules` между машинами запрещено**.

## Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| Починить шимы руками (`создать .cmd`) | Лечит симптом. Нативные бинари всё равно Linux — `build` и `test` не запустятся |
| `npm install --force` поверх | npm считает дерево актуальным по lockfile; чужие optional-бинари он не заменит |
| Оставить как есть, работать через `node node_modules/...` | Временный костыль для меня. Команда из четырёх человек не будет помнить магические пути |
| Работать только на Linux-машине | Команда 007 — кроссплатформенная (Windows/macOS). Отказ от Windows = отказ от половины команды |
| Docker/контейнер для разработки | Правильно в долгую, но это недели настройки и отдельный ADR. Сейчас нужен час работы и зелёный `npm test` |

## Последствия

**Плюсы**
- Появляется **локальная обратная связь** — precondition для всех остальных волн.
- `npm run typecheck` / `lint` / `test` / `build` начинают работать на Windows → гейты в CI обретают смысл.
- Снимается риск «у меня работает, у тебя нет» между Windows и macOS/Linux.
- Проверка платформенной чистоты в CI превращает разовую находку в **постоянный контроль**.

**Минусы / чем платим**
- Полная переустановка зависимостей: ~2–5 минут и трафик. Однократно.
- Нужно выносить рабочую копию из OneDrive — это организационное изменение, а не техническое. Требует решения Никиты.
- `.git` весит 100 МБ; при переносе копии это тоже время. Решается отдельно (ADR-0011).

## План внедрения

| Шаг | Действие | Проверка |
|---|---|---|
| 1 | Согласовать вынос рабочей копии из OneDrive | ✅ решение Никиты |
| 2 | Исключить `node_modules` из облачного синка | файлы не уезжают |
| 3 | `rm -rf node_modules && npm ci` | `.bin/*.cmd` > 0, `binding-win32-x64-msvc` на месте |
| 4 | Прогнать шесть npm-скриптов | 5 из 6 работают (см. DoD) |
| 5 | Добавить `scripts/check-native-bindings.mjs` + шаг в CI | гейт зелёный на чистом checkout |
| 6 | Зафиксировать **реальный** baseline тестов в REGISTRY | число, а не легенда |

**Откат:** обратная операция — вернуть старый `node_modules` из корзины. Риск нулевой: `node_modules` в git не входит, код не трогается.

## Критерий успеха (DoD W−1)

- [ ] `npm run typecheck` выполняется и выводит **307** (число подтверждено, не «упала»)
- [ ] `npm run lint` выполняется (сколько бы ошибок ни было — важно, что запускается)
- [ ] `npm run test` выполняется → **реальное** число тестов записано в REGISTRY (вместо легенды «761»)
- [ ] `npm run build` собирает `dist/`
- [ ] В CI добавлен гейт платформенной чистоты

> **DoD этой волны — не «ноль ошибок», а «проект запускается».** Ошибки будем считать следующей волной, когда появится чем.
