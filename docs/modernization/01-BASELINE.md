## 1. Главное открытие: машина разработки не может запустить проект

Это не «много технического долга». Это **сломанный инструмент измерения**, и именно он породил весь остальной долг.

### 1.1 `node_modules` — это Linux-установка, засинхронённая на Windows

```
node_modules/@rolldown/binding-linux-x64-gnu/rolldown-binding.linux-x64-gnu.node
node_modules/@rolldown/binding-linux-x64-musl/rolldown-binding.linux-x64-musl.node
node_modules/@rollup/rollup-linux-x64-gnu/rollup.linux-x64-gnu.node
node_modules/@rollup/rollup-linux-x64-musl/rollup.linux-x64-musl.node
node_modules/lightningcss-linux-x64-gnu/lightningcss.linux-x64-gnu.node
node_modules/lightningcss-linux-x64-musl/lightningcss.linux-x64-musl.node
node_modules/@esbuild/linux-x64/
```

**Ни одного Windows-бинаря нет.** При этом `package-lock.json` — **корректный**: в нём есть `@rolldown/binding-win32-x64-msvc@1.0.1` с `os: ["win32"], cpu: ["x64"]`. npm на Windows **никогда** не установил бы `linux-x64`-бинари.

**Вывод:** `node_modules` не устанавливался на этой машине — он **приехал готовым** (OneDrive-синк с Linux-машины). Это прямое материальное подтверждение риска **R1** из `TEAM-007-ENGINEERING-PROCESS.md`.

### 1.2 Следствие: `node_modules/.bin` неисполним на Windows

```
$ head -c 60 node_modules/.bin/tsc
#!/usr/bin/env node
require('../lib/tsc.js')

$ ls node_modules/.bin/*.cmd | wc -l   →  0
$ ls node_modules/.bin/*.ps1 | wc -l   →  0
```

`node_modules/.bin` содержит **32 Unix-shell-шима и ни одного `.cmd`/`.ps1`**. Windows-npm не может выполнить ни один.

### 1.4 ⚠️ Почему это объясняет все 307 ошибок

Раньше я записал диагноз «нормализованная терпимость к ошибкам компилятора». Это была **фиксация симптома**. Причина теперь видна:

```
node_modules приехал с Linux
        │
        ▼
npm-скрипты мертвы на Windows  ──▶  локальной обратной связи нет вообще
        │
        ▼
проверка только в CI (ubuntu)  ──▶  там всё зелёное, машина «не при делах»
        │
        ▼
в CI НЕТ шага typecheck        ──▶  307 ошибок не видит никто и никогда
        │
        ▼
«канон 296» становится фольклором  ──▶  цифру передают orally, она протухает
        │
        ▼
никто не чинит то, что не может увидеть
```

**Практический вывод:** нельзя требовать от команды «ноль ошибок tsc», пока `tsc` на их машине не запускается. Любой гейт, который нельзя прогнать локально, будет обойдён — не из вредности, а потому что это единственный способ работать.

> **Поэтому роадмап меняется.** Перед MISSION ZERO (типы) встаёт **W−1 «Оживить машину»**. Без неё MISSION ZERO превращается в бумажную победу: я добью ноль ошибок в своём отчёте, а команда физически не сможет это подтвердить и удержать.

## 2. Реестр не может синхронизироваться — причина найдена

В прошлой сессии я зафиксировал загадку: реестр, который Никит читает на сбросе контекста, **отсутствует в Windows-копии**, хотя должен лежать в git. Гипотеза была «лежит на Linux-машине и не запушен».

**Гипотеза неверна. Причина в `.gitignore`.**

```
$ git check-ignore -v docs/agents/REGISTRY.md
.gitignore:76:docs/agents/     docs/agents/REGISTRY.md        → IGNORED
$ git check-ignore -v docs/sync/MASTER-SYNC-REGISTRY.yaml
.gitignore:66:docs/sync/       docs/sync/MASTER-SYNC-REGISTRY.yaml → IGNORED
$ git check-ignore -q docs/ARCH-BASE.md  → IGNORED
```

`docs/agents/**` — **загитignoreн целиком**. Реестр не «не запушен» — он **не может быть запушен**. Он физически не покидает машину, на которой создан. Никакой синк, никакой git-пуш, никакая вторая копия его не получит.

### 2.1 Масштаб: документация, невидимая для git

| Метрика | Значение |
|---|---|
| `.md`-файлов в `docs/` на диске | **125** |
| из них отслеживается git | **58** |
| **невидимо для git** | **67 (54%)** |

Полный список проигнорированного:

| Путь | Файлов | Что теряется |
|---|---|---|
| `docs/agents/` | 7 | **REGISTRY.md**, AUDIT, MATRIX, PROTOCOL, MODEL-CATALOG, MODEL-ROUTING-GUIDE, README |
| `docs/sync/reports/` | 58 | SYNC-ARCH-01…28, SYNC-CANON-01…05, SYNC-VERIFY-01…05, TC-ARCH-*, TCOV-01 |

### 2.2 ⚠️ Сломанный CI-гейт, который приучил команду игнорировать красный свет

`.github/workflows/doc-sync-check.yml` делает на каждом PR:

```yaml
- name: Check MASTER-SYNC-REGISTRY.yaml exists
  run: |
    if [ ! -f docs/sync/MASTER-SYNC-REGISTRY.yaml ]; then
      echo "❌ MASTER-SYNC-REGISTRY.yaml not found!"
      exit 1
    fi
```

Файл **загитignoreн** → на чистом checkout в CI его **не существует никогда** → шаг делает `exit 1` → **джоба красная на каждом PR, всегда, с момента создания**.

Это не гипотеза: `docs/sync/` даёт 0 отслеживаемых файлов, а `actions/checkout` материализует только отслеживаемое.

**Почему это важно больше, чем кажется.** Гейт, который красный всегда, перестаёт быть сигналом и становится фоном. Команда привыкает не читать CI. А ровно в этом месте и проходят 307 ошибок typecheck — потому что **в CI нет шага typecheck**, и привыкший к фоновому красному свету человек не замечает отсутствия зелёного.

### 2.3 ⚠️ `belive-api/` — вложенный репозиторий (тревога снята, но есть что чинить)

**Первоначальная (неверная) гипотеза.** Я увидел `git ls-files belive-api → 0` при 59 файлах на диске и записал это как «сервис исчезнет без следа». **Это ошибка, и я её здесь исправляю.**

**Что на самом деле.** `belive-api/` — **отдельный git-репозиторий** со своим `.git/` и своим remote:

```
$ cd belive-api && git remote -v
origin  https://github.com/side-chaine/belive-api.git
$ git log -1 --format="%h %ad %s" --date=short
e4ac77f 2026-06-07 fix: UTF-8 safe base64url via TextEncoder/TextDecoder
$ git rev-list --count HEAD
3
$ git status --porcelain | wc -l
6
```

Сервис **забекаплен**. `.gitignore:77` здесь ни при чём — вложенный репозиторий git не отслеживает по определению.

**Но четыре вещи всё равно требуют внимания:**

| Находка | Значение |
|---|---|
| Всего коммитов: **3** | история практически отсутствует |
| Последний коммит: **2026-06-07** | ~3 месяца без активности |
| Незакоммиченных файлов: **6** | в т.ч. изменения в `src/auth/*` |
| Публичный API не отдаёт метаданные репозитория | вероятно приватный — нужно подтвердить |

**Плюс проверка безопасности (пройдена):** `wrangler.toml` не содержит захардкоженных секретов — `GOOGLE_CLIENT_SECRET` и `JWT_SECRET` поднимаются через `wrangler secret put` и в файле только перечислены комментарием. ✅ Так и надо.

**Вывод:** не авария, а **забытый сервис**. Правильная формулировка задачи — «закоммитить 6 висячих файлов и подтвердить, что remote живой», а не «спасать потерянный код».

### 2.4 ⚠️ Репозиторий ПУБЛИЧНЫЙ — это переопределяет решение

```
$ curl https://api.github.com/repos/side-chaine/beLive
private    : false
visibility : public
has_pages  : true        ← GitHub Pages активен
size       : 97 906 KB
```

**Почему это меняет всё.** Моя первая реакция на §2.1 была: «убрать `docs/agents/`, `docs/sync/` и `belive-api/` из `.gitignore` — и реестр поедет». **Это было бы ошибкой.**

Комментарий в `.gitignore` говорит сам за себя:

```gitignore
# Internal docs — not for public
docs/archive/
docs/ARCH-BASE.md
docs/protocol-v2.1.md
docs/sync/
...
# Internal agent docs
docs/agents/
```

Игнорирование внутренних документов — **не халатность, а осознанная мера**. Репозиторий публичный, там же крутится GitHub Pages. Раскомментировать эти строки = выложить внутренний реестр, отчёты агентов и архитектурные черновики в открытый доступ.

**Значит, истинная формулировка проблемы другая.** Не «gitignore сломан», а:

> **Проекту нужны две площадки с разным уровнем доступа: публичная (код + Pages) и приватная (внутренние доки). Сейчас есть только публичная, поэтому внутренние доки существуют ровно на одной машине и нигде больше.**

Отсюда следует, что:
- сделать реестр синхронизируемым **и** оставить репозиторий публичным — можно только заведением приватного репозитория ([ADR-0011](./ADR-0011-git-and-doc-visibility-policy.md));
- цена ошибки при «быстром исправлении gitignore» — **публичная утечка внутренних документов**, необратимая (git-историю чистят только переписыванием).

**Побочная находка:** GitHub Pages на приватном репозитории требует платного плана. Значит «сделать репозиторий приватным целиком» — не бесплатное решение: придётся выносить Pages в отдельный публичный репозиторий. Это вариант рассматривается в ADR-0011, но не рекомендуется.

### 3.1 ⚠️ Проверено запуском: `exclude` не убирает FROZEN-ошибки

[ADR-0001](./ADR-0001-legacy-isolation-project-references.md) изначально предлагал исключить FROZEN-файлы через `exclude` в `tsconfig.json` и получить 307 → 300. **Я это проверил, и это не работает:**

```
$ tsc --noEmit -p <config с exclude всех 4 легаси-путей>
307 ошибок                          ← ожидалось 300
$ ... | grep AudioEngineV2.ts
src/audio/core/AudioEngineV2.ts     ← файл ВСЁ ЕЩЁ в графе компиляции
```

**Причина:** `exclude` фильтрует только `include`-глоб. Файл попадает в компиляцию, если его статически импортирует кто-то из включённых:

```
src/App.tsx
  └─ import { tryActivateV2 } from './audio/featureFlag'
       └─ import { patchV1WithV2 } from './compat/patchV1'            ← FROZEN
            └─ import { AudioEngineV2 } from '../core/AudioEngineV2'  ← FROZEN, 7 ошибок
```

Граница минимальна — **один импорт в `App.tsx`**. Но `App.tsx` в активной работе Никиты, а разрыв связи потребовал бы изменения рантайма (момента патча живого аудио-движка). Поэтому ADR-0001 пересмотрен: **цель W1 = 7, а не 0**; ноль достигается в W2, когда V2 удалят физически.

63 пакета числятся прямыми зависимостями, но **нигде не импортируются** — это транзитив eslint/ajv/js-yaml, попавший в `devDependencies`. Примеры: `minimatch`, `chalk`, `ansi-styles`, `brace-expansion`, `find-up`, `p-limit`, `flat-cache`, `estraverse`, `levn`, `optionator`.

**Вред ровно два:**
1. `minimatch@^3.1.2` и `brace-expansion@^1` как прямые — версии семилетней давности, навязанные всему дереву; современный eslint хочет `minimatch@^10`. Дубли в дереве, непредсказуемая резолюция.
2. **Ложная картина долга.** Вот что это даёт на практике:

| Метрика | Как выглядит | На самом деле |
|---|---|---|
| Устаревших пакетов | **61** | 25 реальных + **36 мусорных** |
| Отставаний на мажор | **44** | **7 реальных** + 37 мусорных |

**Истинный тулчейн-долг — 7 мажоров, а не 44:**

| Пакет | Здесь | Latest |
|---|---|---|
| typescript | 5.9.3 | **7.0.2** |
| vite | 5.4.21 | **8.2.2** |
| jsdom | 28.1.0 | **30.0.1** |
| globals | 14.0.0 | **17.11.0** |
| vite-plugin-pwa | 0.20.5 | **1.3.0** |
| vite-tsconfig-paths | 5.1.4 | **6.1.1** |
| @testing-library/jest-dom | 6.9.1 | **7.0.1** |

Плюс один реальный минорный разрыв в `dependencies`: `@libraz/libsonare` 1.1.0 → 1.7.2.

**Практический вывод:** задача «обновить 44 мажора» выглядит как квартал работы и потому не начинается никогда. Задача «удалить 63 строки мусора, потом обновить 7 мажоров» — это два вечера. **Порядок важен: сначала чистка, потом апгрейд** — иначе половина работы уйдёт на апгрейд пакетов, которых не должно быть в манифесте.

### 5.3 CSP-поверхность

| Что | Шт | Где |
|---|---|---|
| Инлайн `<script>` | **6** | `index.html:38, 57, 192, 369, 406` (+1 module) |
| Инлайн `<style>` | **4** | `index.html:44, 87, 115, 180` |
| Внешние CDN-скрипты | **9** | MediaPipe, `cdn.jsdelivr.net` |
| `new Blob` | 22 | сериализация кода в другой реалм |
| `audioWorklet.addModule` | 2 | |

⚠️ **Отдельная находка:** 9 скриптов MediaPipe подключены с `crossorigin="anonymous"`, но **без `integrity=` (SRI)**. Любая подмена на CDN исполняется в контексте приложения. Это не «когда-нибудь починим», это **открытая дверь**, и закрывается она одной строкой на скрипт.

Кроме того, скрипты подключены **без версии** (`@mediapipe/camera_utils/camera_utils.js`) — CDN отдаёт «последнюю». Сборка невоспроизводима, а после добавления SRI внезапное обновление файла **сломает приложение**. Поэтому SRI и пин версий делаются вместе.

**Ключевое:** гейта на типы **нет вообще**. `package.json` содержит скрипт `typecheck`, но ни один workflow его не вызывает. 307 ошибок не блокируют ни сборку, ни деплой, ни мердж.

### 6.1 ⚠️ Расхождение версий Node

| Где | Версия |
|---|---|
| Локально (машина разработки) | **22.22.2** |
| CI (`deploy.yml`, `quality-gates.yml`) | **20** |
| `engines` в `package.json` | отсутствует |

Команда разрабатывает на одной версии, а собирает и тестирует на другой. Для обычного кода это незаметно, но для **нативных бинарей это критично**: именно расхождение версий/платформ — тот самый класс проблем, из-за которого здесь сломаны `build` и `test`.

**Рекомендация:** зафиксировать версию явно (`.nvmrc` + `engines` в `package.json`) и поднять CI до 22. Пока это не сделано, любой гейт проверяет **не ту среду, в которой пишут код**.

## 8. Итог: три уровня проблемы

| Уровень | Проблема | Почему это корень |
|---|---|---|
| **L0 — инструмент** | Машина не может запустить проект: Linux-бинари, битые `.bin`, 5 из 6 npm-скриптов мертвы | без локального фидбека любой стандарт неисполним |

| **L2 — код** | 307 ошибок tsc, 541 `as any`, 11 god-файлов, V2-легаси | **следствие** L0 и L1, а не причина |

**Главный вывод сессии:** предыдущий роадмап начинался с W1 «Типы». Это ошибка приоритизации. Правильный порядок:

```
W−1 ОЖИВИТЬ МАШИНУ  ──▶  W0 ГИГИЕНА И ГЕЙТЫ  ──▶  W1 ТИПЫ (MISSION ZERO)  ──▶  …
   (дни, не недели)         (1 неделя)              (4–6 недель)
```

W−1 дешёвый по времени и меняет всё остальное: появляется локальная обратная связь, без которой W1 не удержится.
