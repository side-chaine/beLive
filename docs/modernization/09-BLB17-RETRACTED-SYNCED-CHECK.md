## 2. 🆕 Что я нашла сверху (уже на правильном дереве)

Отзыв не означает «делать нечего». Перепроверив на `a691c2f`, я вышла на
две вещи, которых не было ни у меня, ни у тебя.

### 2.1 ⚠️ Тап построен под VU-метринг, а не под питч

```ts
// a691c2f:src/audio/engine-v3/pipeline/HybridPipelineService.ts:62-64
/** Per-stem AnalyserNode для VU-метринга — параллельный тап после _stretchGains,
 *  никогда не в основном сигнальном пути до destination */
private readonly _stretchMeters: Map<string, AnalyserNode> = new Map()
```

```ts
// :238            meter.fftSize = 256
// :102            this._vocalHallMeter.fftSize = 256
```

**`fftSize = 256`.** На 48 кГц это окно **5.3 мс**. Для YIN-детекции нужно
окно минимум в два периода самой низкой ожидаемой частоты. 5.3 мс даёт
низший определяемый фундаментал ≈ **187 Гц**.

Мужской вокал: E2 = 82 Гц · A2 = 110 Гц · C3 = 131 Гц.
**Бас и низкий мужской голос через этот тап не детектируются вообще.**
Для 80 Гц нужно окно ≥ 25 мс → **`fftSize` ≥ 2048** (42.7 мс).

→ Итог: не «строить тап», а **переразмерить его под питч**. Одна строка,
но её надо сделать **сознательно**, а не унаследовать от VU.

### 2.2 ⚠️ Тап НЕ твой — он общий, и менять `fftSize` опасно

`git grep getStemAnalyser` по `a691c2f` даёт действующих потребителей:

| Потребитель | Как читает |
|---|---|
| `src/hooks/useStemWaveform.ts:122-123` | `window.__belive.pipeline.getStemAnalyser(stemId)` ?? `ae.getStemAnalyser` |
| `src/foundation/event-bus/wrappers/stem-reactive.ts:55-56` | то же, `'drums'` |
| `src/bridges/stem-reactive.bridge.ts:93` | `ae.getStemAnalyser?.('drums')` |
| `js/audio-facade-v3.js:35` | `getStemAnalyser() { return null; }` — **фасад его глушит** |

**Два вывода:**

**① Хорошая новость — прецедент уже есть.** `useStemWaveform` **уже читает
V3-тап напрямую** через `window.__belive.pipeline`, с фолбэком на фасад.
Пичу нужно сделать ровно то же самое. Это не проектирование, а копирование
существующего паттерна — объём ещё меньше, чем ты думал.

**② Плохая новость — узел один на всех.** Если поднять `fftSize` 256 → 2048
на `_stretchMeters`, мы **изменим поведение** `useStemWaveform` (сейчас
128 частотных бинов) и `stem-reactive`. Это не поломка, но это незаметная
смена данных для двух подписчиков.

→ **Рекомендация:** не мутировать общий метр-узел. Либо завести **второй
`AnalyserNode`** на том же `stretchGain` с большим окном и отдать его пичу,
либо явно подтвердить, что подписчики переживут смену разрешения.
**Это micro-решение, но его надо принять, а не проскочить.**

### 2.3 Уточнение по тапу: он ПОСТ-fader

`:599` — *«AnalyserNode стема … тап после volume+mute+solo (366)»*.

Для VU это правильно. Для **референса** — вопрос: если педагог приглушит
фэйдер вокала, эталонная кривая пропадёт вместе со звуком. Возможно, так
и надо (студент не слышит → и мерить нечего). Но это **решение, а не
умолчание** — предлагаю зафиксировать его в ТЗ шага ②, чтобы потом не
ловить «питч пропал» как баг.

### 2.4 Моя гипотеза «VIS-3 = VIS-4» — снимаю, но с оговоркой

Принимаю опровержение (атомарная загрузка стемов + отдельная ветка фейдера).
