# ADR-0009 · Тестовая стратегия: сначала запустить, потом считать, потом наращивать

**Статус:** proposed · **Дата:** 2026-08-29 · **Волна:** W5 (подготовка — в W−1)
**Связано:** [01-BASELINE §7](./01-BASELINE.md), [ADR-0010](./ADR-0010-dev-environment-and-node-modules-integrity.md), [ADR-0006](./ADR-0006-state-architecture.md)

---

## Контекст

**Тесты сейчас не запускаются вообще.** `npm run test` падает:

```
Cannot find module './rolldown-binding.win32-x64-msvc.node'
```

Причина — Linux-бинари в `node_modules` ([ADR-0010](./ADR-0010-dev-environment-and-node-modules-integrity.md)).

**Отсюда следует неприятное, но важное следствие:** все цифры про тесты в этом проекте — **фольклор**.

| «Канон» | Статус |
|---|---|
| 761 тест | ❌ не подтверждён и не опровергнут — запустить нечем |
| 770 тестов | ❌ то же |
| покрытие ~13% LOC | ⚠️ оценка по LOC-отношению (10 826 / 83 513), не по `--coverage` |

В прошлой сессии я записал расхождение «761 vs 770» как проблему канона. **Это была неверная формулировка.** Подлинная проблема не в расхождении двух чисел, а в том, что **проверить нечем ни одно из них**.

Зато подтверждено другое — **в самих тестах живут ошибки типов**:

| Файл | Ошибок tsc |
|---|---|
| `src/stores/__tests__/medium-stores.test.ts` | 12 |
| `src/stores/__tests__/simple-stores.test.ts` | 10 |
| `src/billy/__tests__/billy-controller.test.ts` | 9 |
| `src/audio/engine-v3/__tests__/BpmSwitchRace100.test.ts` | 8 |

Тесты, которые не проходят проверку типов, — это тесты, которые **проверяют не то, что кажется**. Они могут падать молча или проверять несуществующий API.

---

## Решение

### Принцип

> **Три шага в строгом порядке: запустить → измерить → нарастить.**
> Наращивать покрытие на неработающих тестах — это строить этажи без фундамента.

### Шаг 1 (W−1). Запустить и зафиксировать факт

```bash
npm ci                                   # ставит win32-бинари
node node_modules/vitest/vitest.mjs run  # первый честный прогон
```

Результат записать в REGISTRY: **сколько всего, сколько падает, сколько скипнуто, сколько времени**. Это первое настоящее число в истории проекта по тестам.

### Шаг 2 (W1). Тесты должны проходить проверку типов

39 ошибок tsc в тестах — это не «шум в тестах». Это места, где тест **не проверяет то, что написано**:

- вызов метода, которого нет → тест падает молча или проверяет `undefined`;
- объект не той формы → мок не соответствует реальности.

Включаем тесты в основной compilation unit (сейчас они в него входят, но ошибки тонут в общих 307). После [ADR-0001](./ADR-0001-legacy-isolation-project-references.md)–[0003](./ADR-0003-typed-global-contracts.md) они станут видны и должны быть вычищены.

### Шаг 3 (W5). Пирамида и рост покрытия

```
        ╱╲          E2E (Playwright)     — критические пути: загрузка трека, запись дубля
       ╱──╲         Интеграционные       — стор ↔ сервис ↔ шина событий
      ╱────╲        Юнит                 — чистые функции, парсеры, матчинг
     ╱──────╲
```

| Уровень | Сейчас | Цель |
|---|---|---|
| Юнит | есть, но с ошибками типов | основная масса |
| Интеграционные | слабо | рост за счёт агрегатов ([ADR-0006](./ADR-0006-state-architecture.md)) |
| E2E | `@playwright/test` установлен, использовать негде | 3–5 критических путей |
| Покрытие | ~13% LOC (оценка) | **25%** |

**Аудио-путь — особо.** Типы не поймают рассинхрон и джиттер. Нужны **снапшот-тесты с допусками**: выходной буфер сравнивается с эталоном с допуском по RMS/задержке, а не побайтово. Побайтовое сравнение аудио ломается от любого изменения плагинов и потому не работает.

### 3.1 ⚠️ Отдельно: компонентных тестов нет вообще, хотя инструменты куплены

Замер ([01-BASELINE §5.5](./01-BASELINE.md)):

| Метрика | Значение |
|---|---|
| Тестовых файлов | **62**, все `.ts` |
| `.test.tsx` / `.spec.tsx` | **0** |
| `@testing-library/react` установлен / импортируется | ✅ / ❌ **нигде** |
| `@testing-library/jest-dom` установлен / импортируется | ✅ / ❌ **нигде** |

**62 теста покрывают сторы, сервисы и аудио-движок — и ни одного компонента React.** При этом 5 из 11 god-файлов — UI-монолиты (`TakesPanel.tsx` 1 557, `SyncEditorPanel.tsx` 1 347, `RehearsalLyrics.tsx` 1 067, `TakesControlStrip.tsx` 918, `StepWorkspace.tsx` 886).

Ровно тот слой, который больше всего подвержен регрессу при декомпозиции ([ADR-0006](./ADR-0006-state-architecture.md)), **не покрыт вообще**. Инструменты установлены и лежат нетронутыми.

**Решение:** первые компонентные тесты пишутся **до** разбора UI-монолитов, а не после. Это страховка, а не отчётность. Порядок:
1. разобрать `TakesControlStrip.tsx` (918) — он же первый в списке [ADR-0006](./ADR-0006-state-architecture.md);
2. покрыть извлечённые блоки компонентными тестами;
3. только потом идти дальше по списку god-файлов.

Так декомпозиция перестаёт быть прыжком без страховки.

### 4. Что НЕ надо делать

| Ловушка | Почему |
|---|---|
| Гнаться за процентом покрытия | 25% осмысленных тестов лучше 60% тестов-заглушек. Метрика — не цель |
| Побайтово сравнивать аудио | Ломается от обновления зависимостей. Только с допусками |
| Тестировать FROZEN-код | Он удалится в W2; тесты на него — работа в мусорку |
| Писать тесты до W1 | Тесты с ошибками типов проверяют не то |

---

## Почему не другие варианты

| Вариант | Почему нет |
|---|---|
| Сразу ставить цель 60–80% покрытия | При 39 ошибках типов в существующих тестах рост покрытия увеличивает **ложную** уверенность |
| Переписать тесты на другой фреймворк | Vitest 4 актуален. Проблема не в нём, а в том, что он не запускается |
| Отложить тесты до конца программы | Тогда W1–W4 пройдут без страховки. Храповик по типам ([ADR-0013](./ADR-0013-ci-gate-architecture.md)) — минимум, но его мало |
| Покрыть тестами FROZEN-движок | Он заморожен и будет удалён; тесты станут легаси-балластом |

## Последствия

**Плюсы**
- Появляется **первое достоверное число** по тестам в истории проекта.
- Тесты перестают содержать ошибки типов → начинают проверять то, что написано.
- Агрегаты ([ADR-0006](./ADR-0006-state-architecture.md)) делают интеграционные тесты возможными — сейчас тестировать нечего, всё переплетено.
- Снапшоты с допусками дают страховку для аудио-рефакторингов в W2.

**Минусы / чем платим**
- **До W−1 вообще ничего нельзя измерить.** Это блокирующая зависимость.
- Рост покрытия с 13% до 25% — это месяцы попутной работы, а не спринт.
- E2E на Playwright требует стабильной среды; в аудио-проекте flaky-тесты особенно дороги. Компенсация: минимум сценариев, только критические пути.
- Снапшот-тесты аудио требуют хранения эталонов → место в репозитории. Компенсация: эталоны — короткие, сжатые.

## План внедрения

| Шаг | Действие | Критерий |
|---|---|---|
| 1 | **[ADR-0010]** `npm ci`, тесты запускаются | прогон завершается, число зафиксировано |
| 2 | Реальная цифра в REGISTRY (всего / падает / скипнуто / время) | записано |
| 3 | `vitest --coverage` — первое честное покрытие | записано вместо оценки |
| 4 | Вычистить 39 ошибок tsc в тестах | `tsc` по тестам = 0 |
| 5 | Снапшот-тест аудио-пути с допусками (до W2!) | эталон создан |
| 6 | 3–5 E2E на критические пути | прогон в CI |
| 7 | Правило: новая логика без теста не мержится | в чеклист ревью |

**Откат:** тесты не влияют на прод. Худший сценарий — удалить написанное.

---

## Критерий успеха (DoD W5)

- [ ] Тесты запускаются локально **и** в CI
- [ ] Реальное число тестов и покрытие записаны в REGISTRY
- [ ] `tsc` по тестам = **0**
- [ ] Покрытие ≥ **25%** LOC
- [ ] Снапшот-тест аудио-пути работает (он нужен как страховка перед W2)
- [ ] 3–5 E2E сценариев в CI

> **Критерий надёжности:** перед удалением V2-легаси (W2) аудио-снапшот **обязан существовать**. Без него удаление движка — это прыжок без страховки.
