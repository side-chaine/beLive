# TRIGGER-PROTOCOL (Far/Near Light) · 2026-08-25

**Статус:** DRAFT — создан по прямому GO Босса. Ожидает подтверждения Соннета (его курс-корректор просил не плодить доки до подтверждения Far/Near; этот файл — рабочий протокол связи, не новый термин миграции).

## 0. Принцип проработки (от Босса)
Исследуем миграцию **полностью**. Operator применяет **только** то, что прошло цепочку:
`research (Far/Mac + Near/Hub цепочки) → брифинг (001/002/009/arch-scout) → выбор лучшего решения`.
Шаги, которые не имеют смысла править без тестов — **не применяем вслепую**, но **исследуем и брифим**. В этом и есть проработка. То, что Боссу нужно протестировать в браузере, — оставляем для его проверки; код применяет Operator, финальный вердикт — за браузерными логами Босса.

## 1. Триггер «перед финалкой» (sync-check)
Любой агент (007_Hub / 007_Mac / Sonnet / Operator) перед финальным отчётом Боссу ОБЯЗАН:
1. Прочитать `REGISTRY.md` + `INBOX.md`, найти пометки `@007_Hub` / `@007_Mac` / `@Sonnet` / `@Boss`.
2. Если есть входящее ко мне — ответить (записать ответ в INBOX / письмо).
3. Если есть исходящее коллеге — положить в INBOX / письмо **ДО** финалки.
Никто не теряет сообщение; Босс видит картину целиком.

## 2. Пауза + тайм-ауты (модель)
Агент после финалки «паркуется» (в этом рантайме = выключен, **0 токенов**). Правила тайм-аута проверяются при **следующем пробуждении** (на команду Босса ИЛИ сигнал стража):
- **T1 (~20 мин) — ожидание коллеги** → PC-первичность: принять PC-проверенное допущение, пометить флагом в INBOX, двигаться дальше (без ступора).
- **T2 (~30–60 мин) — ожидание Босса** → не придумывать новых целей; двигать `PLAN-v3.3-CANONICAL`, гонять цепочки, писать промежуточный отчёт в REGISTRY. Босс просыпается в прогрессе, не в тишине.
- **Токены НЕ капают**, пока агент выключен. Поллер = дешёвый скрипт (`grep` INBOX/REGISTRY), **НЕ LLM** — иначе 30-сек поллинг сжигал бы токены.

## 3. Страж (watchdog) — опционально
Лёгкий скрипт раз в 30с: смотрит REGISTRY на свежие `@me`-записи и истёкшие T1/T2, будит нужного агента.
Альтернатива: **wake-on-message** (Босс/коллега пишет → агент просыпается). Решается отдельно (см. вопрос Боссу).

## 8. Оркестрация агентов: последовательность + параллельные скауты (решение Босса, 26.08)
- **Основные агенты цепочки — СТРОГО ПОСЛЕДОВАТЕЛЬНО.** Цепи вида `001→002→001→009` (либо `005→002→009`, `GO_009` = standalone `[009]` и т.п.) гонятся одна за другой: каждый агент видит вывод предыдущего и держит весь контекст. Задача прорабатывается и передаётся логично, без параллельного выполнения основных агентов.
- **СКАУТЫ (разведка, explore/general read-only) — ПАРАЛЛЕЛЬНО, и это нужно.** Скауты НЕ принимают решений — только собирают и подсвечивают фактуру (точные file:line, выводы grep/git, инвентари). Запуск разрешён:
  1. **ДО запуска 001** — пара скаутов готовит необходимую/полезную инфу, чтобы 001 стартовал с готовой фактурой;
  2. **ПО ХОДУ прогона** — ведущий агент (Мак) сам решает, когда и сколько ещё скаутов запустить для подпитки контекстом (напр. перед 002 для атаки на конкретные находки 001, или перед финальным 009 для проверки пограничных случаев).
- Ведущий агент (Мак/Far Light) единолично решает момент и количество скаутов; цель — чтобы основные агенты не тратили токены на рутинный сбор фактов, а били по существу с полным контекстом.

## 9. Полный контекст на блюдечке (принцип Босса, 26.08)
Каждый запускаемый агент получает **ВСЮ** доступную фактуру сразу — не «пусть сам выясняет»:
- выводы **ВСЕХ** предыдущих агентов цепи (полностью, не саммари);
- релевантные схемы: **кто кого слушает** (event/listener map — напр. `ASSISTANT_RESPONSE_COMPLETED` → `CharacterSoundManager` + будущий `avatar.store`; цепь `aiHub.sendMessage.onDone` → звук + аватар), структура волн W1–W5, grep-гейты;
- точные **file:line** доказательства и текущие счётчики;
- зафиксированные решения (REGISTRY, SYNC-письма, вердикты 009, flip-коммит 2395c1e).
Цель: агент бьёт по существу с полным пониманием, **ноль re-derivation** фактов. «На блюдечке» = агент не тратит токены на повторный сбор/переоткрытие уже известного.
