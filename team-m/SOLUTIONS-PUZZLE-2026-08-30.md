### Досье 1-бис/часть-2 · Исполнение диспатча 200 (LOG 20:15, п.230) · A/B-стенд + FFT-грабли

**Д-А. Досье A/B-стенда питча** (ТЗ Соннета → в документ; заявка 005_2 ①, 20:13)
- **Принцип корпуса:** только внешние эталоны (EGG/ларингограф) — PTDB-TUG (TU Graz, реф-ф0 с ларингографа) + MIR-1K (NTHU, 1000 клипов караоке-вокал+аккомпанемент, с готовыми ф0-аннотациями). **Circularity запрещена:** CREPE — только офлайн-судья (ML-эталон), не участник A/B в прод-контуре. Доступ: оба корпуса = институциональные страницы (не качал; проверка лицензии/зеркал — первая задача исполнителя стенда).
- **Метрики:** RPA (±50 центов) — главная; **Chroma-Accuracy ОТДЕЛЬНОЙ строкой** (октавные прыжки YIN не должны прятаться в RPA!); Voicing Recall / Voicing False Alarm; CPU (ms/кадр, performance.now дельта) + latency в живом пайплайне.
- **Кейсы корпуса (по ТЗ):** бас→сопрано · вибрато · фальцет · breathy · **утечка инструментала = стемы beLive, не изолированный вокал** (это наш реальный сигнал с тапа!).
  - **кейс-лист: 005, канал 20:13→20:16** (связка для Суда: бас<150Гц / гроул / чистый вокал — из досье 005-1.11; его пост 20:16 попросил эту строку).
- **Инструменты живого пайплайна (находка, WebAudio-спека):** `AudioContext.baseLatency` + `outputLatency` + `getOutputTimestamp()` — базовая линия задержки; **`AudioContext.playbackStats` → AudioPlaybackStats: underrunEvents / underrunDuration / averageLatency / maxLatency + resetLatency()** — готовый API-счётчик дропов для стенда, нулевая цена.
- Вердикт: 🟢 документ готов к передаче 007 (ТЗ-вход для диспатч-очереди п.7).

**Д-Б. Досье pYIN-FFT-граблей** (4 грабли Соннета → ответы уровня кода; заявка 005_2 ②, 20:13)
- **(а) Zero-padding ≥ 2N−1:** для буфера N=2048 → FFT-размер ≥ 4095 → `next_fast_len` = **4096**. Без паддинга rFFT даёт **круговую** автокорреляцию: сэмплы «заворачиваются» (index mod N) → ACF(τ) загрязнён хвостом→началом кадра; ошибка максимальна на **больших τ = НИЗКИХ частотах** (для 80 Гц τ≈551 — круговое перекрытие затрагивает 27% окна: 2048−551=1497 полезных сэмплов vs 2048 фиктивных). Наш юз-кейс (бас-вокал, rangeClamp 75–1200) = ровно зона поражения → паддинг ОБЯЗАТЕЛЕН, стоимость +1 бит FFT-размера.
- **(б) Block-size в latency-бюджете:** тик 46ms (=2048/44100); FFT-4096 на тик — CPU-оценка ~0.1–0.2ms на M-классе (замер обязателен, playbackStats закроет дропы); окно анализа НЕ растёт (паддинг — нули, не сигнал). Риск: сборка мусора Float32Array(4096) на каждый тик → преаллокация (см. в).
- **(в) Кэш FFT-плана:** в браузере нет FFTW-планов, эквивалент = **один переиспользуемый инстанс FFT-объекта + преаллоцированные буферы** на процессор (инвариант: не `new Float32Array` в тике — создаём один раз в initFromNode/retarget). **Синергия:** в проекте уже живёт WASM-FFT (внутри signalsmith-stretch!) — вопрос 001: можно ли легально переиспользовать её FFT-ядро (лицензия signalsmith = MIT-семейство) или дублируем. Не решение — находка для спека.
- **(г) Running-sum vs честный FFT:** альтернатива FFT — инкрементальное обновление d(τ) скользящим окном (O(N) на тик вместо O(N log N), но накопление fp-дрифта в running-суммах + сложность обработки границ окна). **Протокол вердикта:** мини-бенчмарк в vitest (не в браузере): синтетика 220Гц + белый шум → 10⁴ кадров → (1) max |d_fft − d_naive| (математическая корректность FFT-пути vs текущего цикла) → (2) время/кадр обеих веток → (3) дрифт running-sum: |d_rs(t=0) − d_rs(t=10⁴)| после цикла добавлений/вычитаний. Критерий: FFT-путь принимается при |Δd| < 1e-6 и ≥5× ускорении; running-sum отвергается при дрифте > 1e-4.
- Вердикт: 🟢 грабли закрыты код-протоколом; оба досье = ТЗ-вход для 007 (диспатч-очередь п.7: pYIN-мультипорог + FFT).

## 🔬 Глубокое досье 3.3-DEEP · rnnoise-wasm в V3 (по диспатчу-2 200, п.2)

**Кандидат:** jitsi/rnnoise-wasm · Apache-2.0 · 191⭐ · WASM-сборка RNNoise (RNN-шумодав Xiph)

**Почему слот открыт архитектурно:** наш инвариант **R9** (`MicSourceV3.ts:73`) = `noiseSuppression:false` —
браузерный шумодав отключён НАМЕРЕННО (сырой мик под наш контроль). Значит шумодав мы обязаны сделать своим —
или мики студентов шумят в питче и на мосту. RNNoise = ровно этот слот, Apache-2.0 = безопасен.

**Текущая мик-цепь (факты, file:line):**
- `MicSourceV3` (`src/audio/engine-v3/services/MicSourceV3.ts`) — acquisition+refcount (:33-53), R9-констрейнты (:73);
- Потребители стрима: ① PitchEngine.initFromMic (ARC-2e даёт `micSource.acquire()`-путь — дедуп 82e1c76); ② REC
  (MediaRecorder = **сырые треки, мимо WebAudio-графа!**); ③ MonitorRouter.micInput (`MonitorRouter.ts:101`, коннект
  stream→micInput = **F-2, ещё не подключён** — `MicSourceV3.ts:7`); ④ vmixMicIn-тап (:156, R-канал V-Mix).
- G14: `setMicMonitor` (`MonitorRouter.ts:161-168`) уже компенсирует outputLatency в `_micDelay` — сюда же ляжет
  алгоритмическая задержка rnnoise.

**Интеграция (эскиз, ВЕРИФИЦИРОВАН СКАУТОМ против живого дерева 22:32 — копейка ① 200):**
1. **MicGraphV3** (новый мини-сервис или расширение MicSourceV3): lazy-строит `stream → MediaStreamAudioSourceNode →
   RnnoiseWorklet → GainNode(denoised)`; refcount как у acquire() (паттерн MicSourceV3.ts:33-53 подтверждён).
2. **Загрузка ворклета — по КАНОНУ ПРОЕКТА, не по моей прошлой ошибке:** `public/worklets/` НЕ существует (скаут);
   живой паттерн = Vite-URL как yin-processor: `new URL('./rnnoise-worklet.js', import.meta.url)` → `addModule`
   (референс pitch-engine.ts:122-124 — единственный файловый паттерн в проде). WASM — паттерн libsonare:
   `import('...wasm?url')` (audio-analysis.service.ts:115) → fetch ArrayBuffer → WebAssembly.instantiate ВНУТРИ
   ворклета (в AudioWorkletGlobalScope нет window, но fetch/instantiate доступны — паттерн jitsi).
3. **Потребители переключаются на denoised-узел:** питч-ворклет и мониторы получают чистый сигнал; REC — см. ниже.
4. **G14-патч:** `compMs += rnnoiseDelayMs` (алгоритмическая задержка RNNoise — измерить при интеграции, eval-кадры
   в районе 10-48 мс; jitsi-обёртка не скрывает задержку).

**Двойная ли цепь (вопрос 200)?** — **Фаза-1: ОДНА цепь для WebAudio-потребителей (питч+монитор+V-Mix), REC сырой.**
Обоснование: MediaRecorder пишет сырые треки мимо графа; переброс REC через MediaStreamDestination = фаза-2 (риск:
двойное кодирование, changed timing). Сырой REC = «архивная правда» + parity. Мост-слышимость (главная боль) получает
denoised уже в фазе-1.

**Усилие (подтверждаю верх 200): 8-10 ч:** ворклет+загрузка 2-3 · MicGraphV3 2 · перепроводка потребителей 2 ·

## 🔬 Микро-досье «ARC-2e + pitchy» (по диспатчу-2 200, п.3)

**Контекст:** 007 применяет ARC-2e по своей спеке (наш YIN остаётся). Досье готовится «на будущее решение Суда».

**Что меняем (минимальный диф после ARC-2e):** обёртка-интерфейс `PitchDetectorV3 { detect(buf: Float32Array, sr: number):
{freq, conf} | null }` + вторая реализация `MpmDetector` (npm pitchy@4, 0BSD). Флаг `?algo=yin|mpm` (localStorage) в
PitchTab/pitch.store переключает. Ноль правок движка — обе реализации поверх одного буфера AnalyserNode.

**Что получаем:** MPM (McLeod/NSDF) сильнее YIN в бас-зоне 75-150 Гц (подтверждено 005_2, тема-2 его охоты) — наш
`rangeClamp` срезает именно низ; A/B-стенд на общих стемах даёт данные для решения «дефолт vs эксперимент».

**Критический нюанс (наш USP):** сабгармоник-метрики (subScore/depth = гроул/скрим-прокси) считаются из CMND-кривой
нашего YIN (`yin-detect.ts:139-152`). У pitchy CMND нет → в MPM-режиме distortion-метрики недоступны. Гибрид (pitchy
для F0 + наш YIN для CMND) = двойной CPU — не предлагаю. Решение для A/B: сравниваем ТОЛЬКО frequency/confidence;
дисторшн-фичи остаются аргументом YIN-дефолта.

**Усилие: 2-4 ч** (обёртка+флаг+тоггл). **Гейт:** frozen не тронут (pitch-модуль вне FROZEN-списка). **Вердикт:**
после ARC-2e, как low-risk эксперимент; дефолт не менять до A/B-данных.
