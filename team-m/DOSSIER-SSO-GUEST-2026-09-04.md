## §2 · ГОТОВЫЕ РЕШЕНИЯ ИНДУСТРИИ (то, что просил CEO_1: «спроси сейчас»)

**| I-1 | LiveKit (канон SFU-платформы): серверный JWT с grants — КЛИЕНТ НИКОГДА не подписывает**
УТВ: AccessToken(apiKey, secret, {identity, ttl}) + addGrant({roomJoin, room, canPublish, canSubscribe}) → toJwt(). Токен = JWT HS256, выдаётся ТОЛЬКО серверным SDK; в токене — identity участника + гранты + TTL. «LiveKit SDKs require an access token... JWT-based and signed with an API secret to prevent forgery. They encode participant identity, room information, and specific capabilities».
ДОК: docs.livekit.io/frontends/authentication/tokens (Context7, 04.09).
ПРОВ: живая дока. СКОУП: паттерн «ссылка гостя = серверный токен с ограниченными грантами» — это и есть наша studentTicket, но с identity-клеймом (см. G-3).

**| I-2 | Jitsi: создание комнаты = auth/token, вход гостя = anonymous-домен — та же топология**
УТВ: Jitsi secure-domain (deprecated, но модель): «allow only authenticated users to create new conference rooms... After the room is created, others will be able to join from anonymous domain» — главный домен auth, guest-домен anonymous. Современный путь (token-authentication): authentication="token" (app_id+app_secret) для создателя + отдельный guest VirtualHost для присоединяющихся. Jitsi сам НЕ рекомендует secure-domain в новых сетапах → JWT (как LiveKit).
ДОК: jitsi.github.io/handbook devops-guide/secure-domain + token-authentication (прогон 04.09, «Last updated Sep 4 2026»).
ПРОВ: живые страницы. СКОУП: обе индустриальные модели = «создатель авторизован, гость заходит по упрощённому пути» — наше дерево ИМИ ИЗОМОРФНО.

**| I-3 | Сходимость: два независимых лидера рынка выбрали одну модель**
УТВ: LiveKit (server-JWT+grants+identity) и Jitsi (token для создателя + anonymous для гостя) сходятся в: ① создатель/учитель = полный auth ② гость = серверно-выданный короткоживущий пропуск ③ клиент никогда не видит секретов подписи.
ДОК: I-1 + I-2.
ПРОВ: сравнение двух живых док. СКОУП: это НЕ мнение — структурная сходимость.

## §3 · РАЗРЫВЫ НАШЕГО ДЕРЕВА ПРОТИВ ИНДУСТРИИ (что дешевле закрыть сейчас)

**| G-1 | 🔴 КЛИЕНТСКОЕ подписывание тикета — единственный анти-паттерн против обоих лидеров**
УТВ: deep-link.service.ts:47-49: если в URL «сырой секрет» (без точки) — КЛИЕНТ сам подписывает тикет через signClientTicket(). Это значит: секрет может путешествовать в ссылке → любой, кто перехватил ссылку с секретом, может подписать себе роль TEACHER. LiveKit и Jitsi такого пути не имеют в принципе.
ДОК: скаут (:47-49); I-1/I-2 (клиент не подписывает).
ПРОВ: скаут + сравнение. СКОУП: серверная ветка УЖЕ есть (ticket body.sig используется как есть) → закрытие = убрать клиентскую ветку + nunca не класть секрет в URL (эмиттер ссылок = rooms API). Зона 001, но факт разрыва — мой.

**| G-2 | Тикет без identity — гость анонимен для DO; LiveKit кладёт identity в токен**
УТВ: наш payload = {roomId, role, exp} — НЕТ identity участника; LiveKit-токен несёт identity (+metadata). Для v0.1 (один студент) не больно; для «возвращающегося студента» (Guest→Named→Returning, заморожено) придётся перепроектировать.
ДОК: скаут (payload tickets.ts:13-18); LiveKit AccessToken {identity}.
ПРОВ: сравнение. СКОУП: добавить {identity} в payload = 1 строка серверно + обратная совместимость (старые тикеты без identity валидны) — дешевле сейчас, чем миграция потом. Решение Босса/001.

**| G-3 | Server-side нет различия «гость vs авторизованный студент»**
УТВ: DO видит только role; сервер не знает, OAuth-студент это или skipAuth-гость. Industry-эквивалент: Jitsi guest-домен = ЯВНО помечен. Для Этапа-1 не больно (студент всегда гость); больно при разморозке Named-студентов.
ДОК: скаут; I-2 (guest host отдельный).
ПРОВ: сравнение. СКОУП: решается тем же identity-клеймом (G-2) — поле `guest:true|sub` вместо отдельного канала. Одна правка вместо двух.

**| G-4 | design-debt вокруг: URL воркера хардкод в CI + CORS только prod-origin**
УТВ: deploy.yml:40 — VITE_REHEARSAL_SIGNALING_URL захардкожен в CI (не secrets); CORS = только app.mybelive.com (gateway/rehearsal/src/index.ts:16) — localhost в пролёте.
ДОК: скаут; 200 PM-3 уже ловил «у deploy-rehearsal ноль гейтов».
ПРОВ: скаут. СКОУП: не SSO-вопрос, но в той же зоне — фиксить при ближайшем проходе по rehearsal-воркерам (не отдельная задача).

Новой архитектуры НЕ нужно — CEO_1-опасение «связка не спроектирована» снято разведкой.

3. **{identity} в тикет (G-2/G-3) — рекомендую добавить СЕЙЧАС** (1 строка, обратная совместимость): при разморозке Guest→Named→Returning вернётся «возвращающийся студент» без миграции формата тикетов. Решение Босса: сейчас (дёшево) или в Этапе-2 (дороже).
4. **Student-OAuth (Named-студент) НЕ нужен для v0.1** — Jitsi-гость и LiveKit-гость-токен обходятся без аккаунта; заморозка Guest→Named остаётся в силе. Когда появятся «постоянные ученики» — тот же rooms API выдаст тикет с sub авторизованного студента (G-2 уже всё подготовит).
5. **Связка с Бриф-1**: studentTicket-ссылка + WebRTC-вход = единый вход студента (deep-link → тикет → wss → media). TURN/DTX-карточки моего Бриф-1 стыкуются без изменений.
