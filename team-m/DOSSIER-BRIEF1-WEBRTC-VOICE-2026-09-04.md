## §1 · OPUS ДЛЯ ВОКАЛА: SDP-ТАБЛИЦА «параметр → значение → что слышно» (вопрос-1 брифа)

**| O-1 | usedtx=0 — ДЛЯ ПЕНИЯ ОБЯЗАТЕЛЬНО**
УТВ: DTX при тишине кодирует 1 кадр каждые 400 мс — пауза между фразами студента = лестница из comfort-noise, хвосты/дыхание/легато срезаются.
ДОК: RFC 6716 §2.1.9: «When DTX is enabled, only one frame is encoded every 400 milliseconds»; RFC 7587 §3.1.3: «using continuous transmission is RECOMMENDED unless constraints on available network bandwidth are severe».
ПРОВ: RFC-тексты получены и прочитаны (04.09). СКОУП: речевой телефон DTX=1 ок (Блок A Опуса прав для speech); «пение по сети» v0.2 = DTX=0.

**| O-2 | maxaveragebitrate=64000 — sweet-spot FB mono music**
УТВ: для пения (не речи) — 48-64 kbit/s fullband mono; 64k даёт запас на динамику/атаки.
ДОК: RFC 6716 §2.1.1 + RFC 7587 §3.1.1: «48-64 kbit/s for FB mono music» (против 28-40k для FB speech).
ПРОВ: RFC. СКОУП: браузерный дефолт WebRTC-голоса ~32-40k (речь); пение = осознанный override. Диапазон параметра 6000-510000 (RFC 7587 §6.1).

**| O-3 | stereo=0 достаточно; stereo не нужен пока музыка не идёт по сети**
УТВ: голос-урок = mono; stereo требуется только для стерео-музыки, которая по сети НЕ идёт (Блок A п.2: трек у обоих локально).
ДОК: RFC 7587 §3.4 + §6.1 (stereo default 0; «every receiver MUST be able to receive stereo»); Опус Блок A п.2.
ПРОВ: RFC. СКОУП: v0.2 «пение студента» — тоже mono-достаточно.

**| O-4 | useinbandfec=1 — да для музыкальных атак**
УТВ: in-band FEC пере-кодирует перцептивно важные пакеты (атаки, транзиенты) в следующий пакет — для музыкального урока (attack=суть ритма) включать.
ДОК: RFC 6716 §2.1.7: «Packets that are determined to contain perceptually important speech information, such as onsets or transients, are encoded again at a lower bitrate»; RFC 7587 §3.3.
ПРОВ: RFC. СКОУП: +немного битрейта; плата оправдана при lossy-сети.

**| O-5 | ptime=20 (дефолт) — не трогать**
УТВ: 20 мс кадр = стандарт; уменьшение (10 мс) = −10 мс задержки за ×2 пакетов; для «поправить фразу» (не ансамбль!) — не нужно.
ДОК: RFC 7587 §6.1 ptime default 20, значения 3-120; RFC 6716 §2.1.4: «20 ms frames are a good choice for most applications».
ПРОВ: RFC. СКОУП: v0.2 при желании −10 мс за счёт ptime=10 — мера завтрашняя.

**| O-6 | Механизм мунжинга: SDP a=fmtp (usedtx/stereo НЕ выставляются через setParameters)**
УТВ: maxBitrate — через RTCRtpSender.setParameters({encodings:[{maxBitrate:64000}]}); usedtx/stereo/maxplaybackrate — только правкой a=fmtp строки в SDP до setLocalDescription.
ДОК: MDN sdpFmtpLine: формат `a=fmtp:<pt> param1=value1;...`; HPBN ch.18 SDP-механика; RFC 7587 §7 (таблица маппинга параметров в a=fmtp).
ПРОВ: MDN+RFC. СКОУП: мунжинг ДО setLocalDescription — канонический путь; частичная поддержка параметров в браузерах разная → карточка S-2 (Safari).

**| O-7 | Задержка самого кодека: 5-65.2 мс (наш случай ~26.5 мс)**
УТВ: Opus algorithmic delay = 5-65.2 мс в зависимости от режима; голосовой гибрид FB 20мс ≈ 20+5(SILK look-ahead)+~1.5(ресемпл) ≈ 26.5 мс.
ДОК: RFC 6716 §2: «algorithmic delays ranging from 5 ms to 65.2 ms»; §2: SILK «additional 5 ms look-ahead», «up to 1.5 ms» rate conversion, CELT +2.5 мс look-ahead.
ПРОВ: RFC. СКОУП: это КОДЕК, не сеть — см. §4.

**| O-8 | VBR (дефолт) лучше CBR — не трогать**
УТВ: cbr=0 (дефолт) даёт выше качество при том же среднем битрейте; CBR нужен только для защиты от length-based side-channel (не наш кейс).
ДОК: RFC 7587 §3.1.2: «For the same average bitrate, VBR can achieve higher audio quality than CBR».
ПРОВ: RFC.

**Итоговая SDP-строка пения (старт-точка для 001, НЕ архитектура — фактура):**
`a=fmtp:<pt> maxaveragebitrate=64000; stereo=0; usedtx=0; useinbandfec=1` + `a=ptime:20` — каждый параметр = карточка выше.

## §2 · R9 / AGC / ЭХО: где применяются констрейнты (вопрос-2 брифа)

**| E-1 | Констрейнты живут на getUserMedia + applyConstraints (не на трансивере, не в SDP)**
УТВ: echoCancellation/noiseSuppression/autoGainControl — свойства ЗАХВАТА (MediaStreamTrack), применяются в браузерном аудио-пайплайне до кодера; в WebRTC-отправку идёт уже обработанный (или сырой, если false) сигнал. Меняются после захвата через track.applyConstraints().
ДОК: MDN applyConstraints (пример смены констрейнтов на живом треке); MDN getSupportedConstraints (echoCancellation/noiseSuppression/autoGainControl — поддерживаемые параметры); HPBN ch.18 «acquired audio stream is processed for noise reduction and echo cancellation, then automatically encoded».
ПРОВ: MDN (Context7, 04.09). СКОУП: R9 (MicSourceV3:73, все три false) = в WebRTC уйдёт СЫРОЙ мик — осознанно; echo-решение см. E-2.

**| E-2 | 🔴 Развести EC у пира против raw у питча на ОДНОМ устройстве — констрейнты на клонах НЕ расходятся по спеке. SPIKE-КАРТОЧКА (30 мин, Chrome+Firefox+Safari)**
УТВ: Блок A Опуса п.3 утверждает «клон с echoCancellation:true... клоны позволяют развести констрейнты». Это НЕ гарантировано спекой: clone() создаёт трек с тем ЖЕ источником; applyConstraints применяется к источнику — на практике (Chrome) изменение EC на клоне меняет обработку для всех треков этого источника.
ДОК: MDN clone/applyConstraints (спека: треки шарят source); Блок A п.3 (проверяемое утверждение Опуса).
ПРОВ: MDN-спека НЕ подтверждает расхождение клона — только НЕ опровергает. Живой прогон НЕ делал → честно: ГИПОТЕЗА, требующая спайка: (а) gum raw → clone → applyConstraints({echoCancellation:true}) на клоне → проверить getSettings() обоих + слуховой эхо-тест в WebRTC. (б) если расходятся — Блок A п.3 жив; (в) если нет — half-duplex (уже в Блок A п.3 как полиси) или второй getUserMedia (нарушает инвариант «один getUserMedia» — гейт Блока A п.1 красный → тогда вопрос 001).
ПРОВ: спайк ОБЯЗАТЕЛЕН до Фазы-2 Блока A. СКОУП: это НЕ блокер Фазы-0/1 (греп-гейты, micRegistry).

**| E-3 | Наушники снимают вопрос эха целиком — headphones-first это не эвристика, а архитектурная развязка**
УТВ: студент в наушниках → сигнал учителя физически не попадает в микрофон студента → AEC не нужен вообще → R9-raw в WebRTC безболезнен. Продукт = музыкальные уроки: наушники у практика — норма.
ДОК: физика + Опус Блок A п.3 (half-duplex полиси для колонок).
ПРОВ: рассуждение. СКОУП: полиси-вопрос (продуктовый) — карточка для Босса в РЕШЕНИЕ-КАРТОЧКЕ.

## §4 · РЕАЛЬНЫЕ ЦИФРЫ ЗАДЕРЖКИ (вопрос-4 брифа)

**| L-1 | Что доминирует: сеть + jitter-buffer >> кодек**
УТВ: кодек ≈ 26.5 мс (O-7); jitter-буфер браузера адаптивный 20-60+ мс; сеть = RTT/2 (гео). Итого 1:1 голос типично 100-250 мс end-to-end, из них кодек < 15%.
ДОК: RFC 6716 §2 (кодек); HPBN ch.18 (механика jitter/adaptive playout, «Packet-loss rates and latency between the peers are unpredictable»); ITU G.114 (телефония: <150 мс отлично, 150-400 приемлемо — канон-телефония, по памяти, помечено).
ПРОВ: RFC+HPBN; G.114 — помечено. СКОУП: живые свои цифры = getStats (currentRoundTripTime) — Фаза-2 замер Блока A п.5 уже в спеке.

**| L-2 | Критерий полезности «поправить фразу»: 150-250 мс — ДОСТАТОЧНО (телефон-класс)**
УТВ: поправка фразы = разговорный паттерн, не ансамбль; телефон 150-300 мс приемлем годами. Ансамбль (играть вместе <50 мс) по сети недостижим — и НЕ НУЖЕН: музыка у обоих локально, синхрон через control-канал (Блок A п.2/п.6 — уже канонизировано).
ДОК: см. L-1; Блок A Опуса (п.6: «голос с точностью доли = ошибка архитектуры» — моё досье ПОДТВЕРЖДАЕТ).
ПРОВ: согласование трёх источников. СКОУП: решение не моё — фактура для Босса: голосовой канал не обязан догонять VirtualClock.

**| L-3 | Оба пира за CF-TURN: пакетный-loss стабильнее, raw-latency может НЕ улучшиться**
УТВ: CF сам говорит: TURN-оба-конца rides CF backbone (loss лучше), но «the size of the latency improvement varies by geography» — обещать снижение задержки нельзя, обещать стабильность можно.
ДОК: CF FAQ: «The more consistent improvement from using TURN on both ends is reliability and packet loss behavior, not raw latency».
ПРОВ: FAQ-цитата. СКОУП: не включать оба-конца-TURN «для скорости» — только для пробивания NAT.

**| L-4 | Задержка RNNoise не входит в голос-путь, если денойз только локально (стык §6)** — см. R-1/R-2.

## §5 · ТОЛЬКО-ГОЛОС: addTransceiver vs addTrack + видео-потом (вопрос-5 брифа)

**| V-1 | Добавление видео ПОЗЖЕ без пересоздания соединения — ДА, автоматический renegotiation**
УТВ: WebRTC пересогласовывает SDP при добавлении/удалении треков — соединение НЕ пересоздаётся. «Сначала голос, видео потом» — не тупик.
ДОК: HPBN ch.18: «Once the connection is established, the application can still add and remove streams from the RTCPeerConnection object. Each time this happens, an automatic SDP renegotiation is invoked».
ПРОВ: HPBN. СКОУП: iOS Safari + renegotiation — исторические баги, см. S-1 (не проверял сегодня).

**| V-2 | addTrack для первого трека проще; addTransceiver — для direction-контроля загодя**
УТВ: addTrack(track) вешает трек + триггерит onnegotiationneeded; addTransceiver('audio',{direction}) провижнит m-line без трека. Для 1:1-голоса разницы по накладным НЕТ — m-line один, бандвит = сам звук.
ДОК: HPBN ch.18 (механика addStream/renegotiation); MDN addTransceiver/addTrack (Context7-знание, помечено: страницы не тянул сегодня — механика onnegotiationneeded стандартная).
ПРОВ: HPBN-часть живая; MDN-часть — помечено. СКОУП: выбор метода = 001 (API-механика, не наука).

**| V-3 | DTX для разговора — ок (O-1 не противоречит), но проще единый профиль**
УТВ: разговорный канал может жить с usedtx=1; пение (v0.2) = usedtx=0. Режим фиксируется в SDP на сессию, смена = renegotiation.
ДОК: RFC 7587 §6.1 (usedtx в fmtp); Блок A п.4 («пение = v0.2»).
ПРОВ: RFC. СКОУП: рекомендация-фактура: единый usedtx=0 с 64k — запас копеечный, ЗВОНИТ ЯСНЕЕ; без режимного переключателя.

## §6 · СТЫК С RNNOISE (вопрос-6 брифа)

**| R-1 | WebRTC-трек должен бежать от denoised-узла графа, НЕ от raw-мик-трека**
УТВ: rnnoise-DEEP (цепь 02.09, РЕШЕНО С УСЛОВИЯМИ): MicSourceV3.acquire() отдаёт denoised-стрим. Для WebRTC: педагог должен слышать ЧИСТОГО студента → отправляем denoised-выход. Механически: denoised-Gain → MediaStreamDestination → track → addTrack (новый узел графа, ~15 строк, ЗОНА 001).
ДОК: RNNOISE-001-CIRCLE3-FINAL (file:line живы на 23bed3d, ревизия 13:39 02.09); Блок A п.1 (micRegistry + track.clone()).
ПРОВ: спека-цепь. СКОУП: E-2 спайк решает эхо-вопрос параллельно; без наушников = half-duplex полиси (уже Блок A п.3).

**| R-2 | RNNoise-задержка (10.67-21 мс, G14-компенсирована локально) НЕ удваивается в голос-пути**
УТВ: денойз один раз в графе студента; педагог получает уже чистый сигнал. G14-компенсация — локальный монитор-путь (MonitorRouter), НЕ WebRTC-путь.
ДОК: RNNOISE-002-CIRCLE2 (rnnoiseDelayMs=10.67, формула max(0,43−10.67)); MonitorRouter — локальный путь.
ПРОВ: цепь-спеки. СКОУП: суммарная студента-до-педагога = RNNoise(~10мс) + кодек(~26.5мс) + сеть + jitter — телефон-класс (L-2).

**| R-3 | AEC в браузере НЕ применяется к WebAudio-обработанному треку — headphones-first становится обязательным**
УТВ: browser AEC живёт в getUserMedia-пайплайне ЗАХВАТА; трек из MediaStreamDestination (наш денойз-выход) идёт в WebRTC как уже-обработанный — БЕЗ браузерного AEC/NS/AGC (некуда применить — это не gum-трек).
ДОК: механика E-1 (констрейнты = захват); MDN MediaStreamDestination (создаёт track из графа — Context7-знание, помечено).
ПРОВ: соединение двух MDN-механик (без живого прогона — помечено). СКОУП: наушники/half-duplex — ЕДИНСТВЕННЫЙ эхо-механизм при denoised-треке. Усиление E-3: headphones-first — не опция, а обязательное полиси при R-1 → в РЕШЕНИЕ-КАРТОЧКУ.
