## 1. АТАКИ ПО ПУНКТАМ СПЕКИ (ранжировано по тяжести)

### ① Сервис VoiceProfileV3 — модель/метрики

**УДАР 1 (УБИВАЮЩИЙ): клейм С5 «aperiodicity из yin-detect.ts:147» — поле не существует в YinResult.**
- Спека ① таблица С5: «`yin-detect.ts:147` (aperiodicity) → новое поле msg.aperiodicity (правка ②-б)».
- Живое дерево: `yin-detect.ts:147` — `const aperiodicity = cmnd[te]` — **локальная переменная**. Интерфейс `YinResult` (`yin-detect.ts:10-28`) поля `aperiodicity` **не содержит**; return-объект (`:176-187`) его **не возвращает**. Поле умирает внутри `detect()`.
- Правка ②-б по спеке: `pitch-engine.ts:218-224` — `aperiodicity: (result as any).aperiodicity` → **`msg.aperiodicity = undefined` всегда**. С5-медиана = NaN. Перекрёстная валидация SFM/CMND (ядро ГРАНИЦА-301, «косяк-фильтр») мертва на корню: сравнивать нечего.
- **Сценарий отказа:** юзер проходит калибровку → `finalize()` агрегирует NaN по С5 → либо снапшот с NaN-полем молча персистится как «Слепок снят ✓», либо перекрёстный фильтр (расхождение >δ при undefined) отсеивает ВСЕ кадры → `finalize() → null` → «честный отказ» на каждом прогоне. Оба исхода = слепок не работает.
- **Патч:** правка ②-б расширяется на 2 строки в `yin-detect.ts` (не frozen): `aperiodicity` в интерфейс `YinResult` + в return-объект. Спека обязана это зафиксировать — иначе её «+1 строка в pitch-engine.ts» — правка пустого места.

**УДАР 2 (УБИВАЮЩИЙ): фаза-1 калибровки идёт через initFromMic — а мик-путь не несёт НИ subScore, НИ noiseScore, НИ depth.**
- Спека ④ фаза-1: «PitchEngine-мик (существующий initFromMic-путь) → кадры {f0, conf, sub, noiseSFM, rms}».
- Живое дерево: `initFromMic` (`pitch-engine.ts:78-140`) вешает **AudioWorklet** `yin-processor.js`. Worklet шлёт ТОЛЬКО `{type:'pitch', frequency, confidence, rms, midi, timestamp}` (`yin-processor.js:166-172`) — grep по файлу: `subScore`/`noiseScore`/`depth`/`subharmonicRatio` **отсутствуют целиком**. Вся distortion-телеметрия живёт в **main-thread**-ветке `_passiveTick` (`pitch-engine.ts:210-224`), которая выполняется только в `initFromNode`-режиме.
- Спека ① даёт источники С3/С4 как «`yin-detect.ts:134-145` → msg.subScore (`pitch-engine.ts:222`)» — но `:222` — это `_passiveTick`, а фаза-1 идёт worklet-путём. **Спека смешала два режима движка.**
- **Сценарий отказа:** прогон калибровки → кадры фазы-1 содержат f0/conf/rms/midi, `sub`/`noiseSFM` = undefined → С3 (subScore-медиана) и С4 (SFM-медиана) = NaN → 3 из 8 метрик мусор + перекрёстная валидация снова мертва (нечего сравнивать). Светофор «🟡 SFM высокий при слабом sub» не зажигается никогда — оба поля undefined.
- **Патч:** фаза-1/фаза-2 калибровки идут через **`initFromNode`-путь** (AnalyserNode + main-thread YIN, где живёт вся телеметрия), а не `initFromMic`. Сервис сам создаёт `createMediaStreamSource(stream)` от `MicSourceV3.acquire()` и передаёт узел в `initFromNode`. Это НЕ новая механика — режим Б движка уже жив и протестирован (К-3, `pitch-engine-modes.test.ts:56-77`). Альтернатива (прокинуть телеметрию в worklet-сообщения) — правка audio-thread кода `yin-processor.js`, дороже и не нужна.

**УДАР 3 (СРЕДНИЙ): deviceId-гвард светофора слеп у юзера без выбранного устройства.**
- Спека ④: «🔴 красный: смена микрофона (deviceId ≠ базового) — источник `MicSourceV3.deviceId:29`».
- Живое дерево: `MicSourceV3.deviceId` (`MicSourceV3.ts:29`) возвращает `_deviceId`, который инициализируется из `localStorage 'mic:deviceId'` (`:34`) и **остаётся `''`, если юзер никогда не выбирал устройство**. `_open()` (`:73-88`) **не читает** `track.getSettings().deviceId` после захвата стрима — поле не наполняется фактом.
- **Сценарий отказа:** юзер с дефолтным миком (deviceId='') выдёргивает USB-мик, браузер подменяет устройство на дефолт → acquire возвращает новый стрим → `_deviceId` по-прежнему `''` → гвард видит `'' === ''` → «стабилен» → снапшот склеивает кадры с двух разных микрофонов молча. Красный-кейс «микрофон сменился» не срабатывает никогда у юзеров, не выбиравших устройство руками (большинство).
- **Патч:** светофор берёт deviceId из `stream.getAudioTracks()[0].getSettings().deviceId` на каждом acquire (сравнение с базовым первого кадра), а не из стора MicSourceV3. Либо спека честно фиксирует: гвард работает только при exact-выборе устройства.

**УДАР 4 (СРЕДНИЙ): порог «расщепного кадра» для С7/С8 не определён — семантика будет изобретена на месте.**
- Спека ①: С7 «faderAtSplit — медиана по „расщепным" кадрам», С8 «splitMargin — расстояние sub/noise при расщепе». Нигде в спеке нет порога: что такое «расщепной кадр»? subScore > 0.2? > 0.3? Решение юзера (когда он «достиг расщепа»)?
- **Сценарий отказа:** реализация 001-ревизии выбирает порог наугад → С7/С8 у двух реализаций не совпадают → снапшоты несравнимы между сессиями/версиями → «точка отсчёта конкретного пользователя» плывёт.
- **Патч:** спека фиксирует порог явно. Дешёвый канонический кандидат: `subharmonicRatio > 0.2` — прецедент уже в живом коде (`yin-detect.ts:189` — порог осмысленности subFrequency). Одна строка в спеке.

**УДАР 5 (МЕНЯЙ ПОРОГ — МЕЛКИЙ): светофор путает rms-пороги.**
- Спека ④: «🟢 RMS в гейте (0.003 < rms < 0.5 — порог тишины уже есть `pitch-engine.ts:230`)».
- Живое дерево: `0.003` в `pitch-engine.ts:230` — порог ветки «real silence vs scream-no-pitch» внутри `_passiveTick` (решает, слать `no_pitch` или `silence`), а **гейт YIN = 0.01** (`yin-detect.ts:41` `_gate`). Кадры с rms < 0.01 вообще не доходят до msg-канала как pitch — они приходят как `{type:'silence', rms: 0}`.
- **Сценарий отказа:** quality-логика, проверяющая «0.003 < rms», пропускает rms ∈ [0.003, 0.01) как «валидные» — а это уже зона YIN-гейта, где детектор молчит. Мелочь, но светофор должен слушать `msg.type` + rms, а не голое число.
- **Патч:** красный-кейс «тишина» = `msg.type === 'silence'` (уже дискретен в канале), rms-проверка — только верхняя граница (клиппинг < 0.95).

### ③ Фейдер-цепь WaveShaper

**УДАР 6 (СРЕДНИЙ): observer-effect — сатуратор меняет поведение юзера, снапшот пишет артефакт.**
- Спека ③: equal-power dry=1−x / wet=x, «жёсткий tanh-сатуратор». ④: «юзер водит фейдер и СЛЫШИТ».
- **Сценарий отказа:** громкий вокал (rms 0.3+, что в гейте спеки — валид) + фейдер → 1 → tanh-квадратура поднимает воспринимаемую громкость wet-сигнала → юзер инстинктивно поёт тише → С7 (faderAtSplit) и фаза-2-кадры пишутся с **придушенным голосом** → снапшот «расщепа» систематически смещён относительно реального пения без наушников-обратной связи. Светофор этого не ловит: rms-гейт 0.003–0.5 пропускает придушенный голос как «зелёный».
- **Проверка удара:** ломается на входе «громкий вокал + фейдер высоко» — не экзотика, а штатный кейс фазы-2. Спекой не пойман.
- **Патч:** `wetGain = x × 0.5` (−6 дБ компенсация сатурации) — одна константа в split-fader.ts, суть спеки не меняет. Плюс опционально: светофор сравнивает медиану-rms фазы-2 с фазой-1 (дрейф > ×0.5 → жёлтый).

**УДАР 7 (МЕЛКИЙ): outGain → destination при gain=0 — узел-зомби в графе.**
- Спека ③: `outGain.gain.value = 0` по умолчанию, включается кнопкой. Узел подключён к `ctx.destination` постоянно.
- **Сценарий отказа:** технической петли нет (гейн 0 = тишина), но: (а) в V3-архитектуре маршрутизация звука идёт через MonitorRouter (main.tsx:174 публикует router) — прямой `→ destination` в обход роутера = второй маршрут мика в графике, дублирующий будущий F-2; (б) dispose-тест 7 проверит disconnect, но «зомби-период» (цепь жива, гейн 0) не покрыт никаким инвариантом.
- **Патч:** подключение `outGain → destination` делать лениво — в момент включения 🎧 (connect/disconnect парой), не в конструкторе. Дешевле, чем тянуть MonitorRouter в скоуп, и убивает зомби-маршрут by design.

### ② Снос PitchTab

**УДАР 8 (СРЕДНИЙ): снос EMA-хука роняет hold-500ms — vocal-дисплей начинает мигать.**
- Спека ②: снос `useStableVocalData` (`PitchTab.tsx:101-185`) → vocal-движок на `useStableNote` (`:187-219`).
- Живое дерево: `useStableVocalData` держит последнюю ноту 500 мс при no_pitch/silence (`:157-163` — holdMs-логика). `useStableNote` **hold-а не имеет** — `else setNote(null)` сразу (`:213-215`). Тикер ~21.5 Гц шлёт silence/no_pitch между фразами вокала.
- **Сценарий отказа:** после сноса vocal-нота в PitchTab мигает на каждой паузе между фразами (21.5 Гц null↔note) → регрессия живого UX в паке, заявленном «слепок = 100% новый код + 2 точечные правки». PianoKeyboard (`vocalNote={vocal.note}`) дёргается на каждый null.
- **Патч:** при сносе перенести hold-500ms в `useStableNote` (3 строки, паттерн уже написан в соседнем хуке). Спека обязана это зафиксировать в ②, иначе «снос» — не снос, а замена с потерей поведения.
