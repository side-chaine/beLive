## §1. АТАКА ① — два стенда: Node-офлайн (вердикт) + браузер-vignette (витрина)

**УДАР 1-1 (sr-расщепление):** harness нарезает WAV-кадры 2048 при родном sr файла. Стем 48kHz → кадр покрывает 42.7ms, стем 44.1kHz → 46.4ms; tauMax=1024 → нижняя граница детекции 48000/1024=**46.9Гц** против 44100/1024=**43.0Гц**. Прод живёт на `ctx.sampleRate` юзера (44.1к/48к — зависит от железа). Вердикт «C лучше A на басе» может быть артефактом sr конкретного набора стемов, необобщаемым на прод. **Ловится:** manifest со стемами разного sr (студийные WAV часто 48к) — первый же прогон. → **Патч:** `manifest.json` получает обязательное поле `sr` + harness-ассерт единообразия (или ресемплинг к каноническому sr); в results-JSON пишется sr. Дёшево, до прогона.

**УДАР 1-2 (autoCal-излом внутри метрической зоны):** warm-up 1.5с = ~32 кадра, но autoCal срабатывает после **50** конф-кадров (`yin-detect.ts:146-149`, `:193-198`) → на кадре ~50 (≈2.3с) `_rangeClamp` меняет lo/hi: для бас-стема (med<200) hi падает 1200→**600** → все ноты >600Гц после 2.3с принудительно делятся /2 (`yin-detect.ts:174-178`). Метрики A получают излом посередине файла: RPA/Chroma бас-стема меряют два разных детектора (до/после autoCal). **Ловится:** бас/гроул-стем с выходом выше 600Гц после 2.3с (гроул → фальцет-переход — ровно целевой кейс VIS-14). → **Патч:** (а) warm-up 2.5с+ (>50 кадров) — если пак v1.4 позволяет; (б) если 1.5с заморожен паком — metrics.ts пишет в JSON `autoCalAt: frameN` per-file, и вердикт-правило §2 интерпретирует бас-кейс с оговоркой. **УДАР 1-3 (витрина = псевдо-вердикт для публики):** мок `octave-sweep` спроектирован как «money-shot» под сильную сторону C (спека ⑤-1 сама это называет). ## §2. АТАКА ② — pyin-c.ts переезжает в src/audio/pitch/pyin-vote.ts

## §3. АТАКА ③ — AudioWorklet/GPU в harness = НЕТ

Аргументация 001 (Node не имеет AudioWorklet; GPU в WebAudio нет; детерминированность) — **крепкая, атаке не падает**. Но решение имеет непроговорённое следствие:

**УДАР 3-1 (вердикт меряет main-thread-A, а прод-A — два разных A):** живое дерево уже содержит ДВА A с разной no_pitch-семантикой:
- `yin-detect.ts:104-107`: te===-1 → **te = minTau** → detect() возвращает freq=sr/minTau с conf=1−minVal (может быть 0.2–0.5) — «питч из шума»;
- `yin-processor.js:132-135`: te===-1 → **no_pitch, return** — честный отказ.

Стенд (② bench-runner, контур A = импорт YinDetector) меряет main-thread-семантику. Это КОРРЕКТНО для vocal-тапа (прод-vocal = `_passiveTick` → `yin-detect.ts`, `pitch-engine.ts:208`), но значит: (а) вердикт-JSON обязан фиксировать `aSemantics: main-thread-fallback`, иначе читатель не знает, какой из двух A проиграл/выиграл; (б) fallback-семантика сама по себе — живой дефект vocal-пути (мусорные питчи на шумовых кадрах с conf≤0.85), и стенд покажет его как «минус A» — это честно, но должно быть названо, а не выглядеть как «A плох». **Ловится:** любой стем с шумовым интро/бриджем — первый же прогон. → **Патч:** (1) results-JSON: поле `aSemantics` + примечание о worklet-расхождении; (2) опционально (дёшево, без правки yin-detect): A-обёртка в contours.ts с флагом `workletMode: if (r.confidence <= 0.85) return null` — воспроизводит worklet-семантику на том же ядре (worklet принимает только cmnd<0.15 ⇔ conf>0.85), даёт вторую колонку «A(worklet-семантика)» для полноты картины. Оба варианта не трогают frozen-подобные зоны yin-detect.

**УДАР 3-2 (latency-числа витрины = шум):** витрина меряет `performance.now` вокруг detect в браузере, где параллельно тикают PitchEngine-vocal (46ms), V3-пайплайн, мониторы. Числа «0.8ms/f» будут прыгать от машины к машине и от загрузки — а выглядят как измерение. **Ловится:** любой DEV-прогон с играющим треком. → **Патч:** подпись в vignette: «latency indicative; CPU-вердикт = Node-стенд» (строка в signage ⑤, 0 логики).

**УСИЛЕНИЕ ③:** A-обёртка `workletMode` (удар 3-1, вариант 2) — +5 строк в contours.ts, превращает известное расхождение в измеряемую колонку вместо скрытого смещения.

**ВЕРДИКТ ③: ТРЕБУЕТ ПАТЧА** (лёгкого) — держит при условии: aSemantics-фиксация в JSON; latency-дисклеймер. Сам отказ от AudioWorklet/GPU — ДЕРЖИТ безусловно.

## §4. АТАКА ④ — стенд-движок = отдельный сервис bench/pitch-stand.ts (не PitchEngine)

Довод «PitchEngine = ARC-2e-минное поле» верифицирован: singleton `pitch-engine.ts:27-31`, gen-гварды `:44/:72`, refcount `:260-262`, `_passiveTick` `:202-235` — прививка стенда туда расширяла бы мины. Отдельный сервис — правильно. Но:

**УДАР 4-1 (HMR-зомби):** DEV-витрина живёт в Vite-HMR. Правка любого модуля в графе импортов → модуль-свайп; React.lazy-компонент при этом НЕ всегда размонтируется корректно (HMR не полный unmount) → старый экземпляр pitch-stand с живым setInterval(46) остаётся тикать вечно, новый создаётся рядом → двойные тики, каунтеры врут, консоль шумит. **Ловится:** каждая правка кода при открытой витрине — то есть постоянно в DEV-режиме разработки. → **Патч:** в модуле StandVignette: `if (import.meta.hot) import.meta.hot.dispose(() => standRef.current?.destroy())` — прецедент в живом дереве: `main.tsx` (import.meta.hot.dispose → cleanupAll/bridgeFacade.destroy). 3 строки.

**УДАР 4-2 (async-B рассинхронизирует counters):** B (pitchy) грузится `dynamic import('pitchy')` внутри pitch-stand (спека ④, double-защита). setInterval стартует сразу → первые N тиков (пока промис резолвится) кадры уходят в A и C, но не в B → `aLies/bLies/fixedByC` считаются на разных подмножествах кадров → «A-лжи 12 → C 2» на экране несравнимо. **Ловится:** первый же прогон витрины (динамический импорт с диска/кэша всегда медленнее первого тика). → **Патч:** тики стартуют после `Promise.all` готовности контуров (B-обёртка резолвится до первого setInterval); или до готовности B стенд не инкрементит счётчики A/C (хуже — теряются кадры). Первый вариант: +3 строки в init.

**УДАР 4-3 (PS-2 не ловит HMR-случай):** тест PS-2 «stop/destroy → таймер убит» тестирует явный destroy, но HMR-сценарий (удар 4-1) — неявный, без destroy-вызова. Тест зелёный, зомби жив. **Ловится:** не ловится тестом — ровно в этом проблема. → **Патч:** PS-2 расширяется: после destroy повторный create + destroy (симуляция свайпа) → assert «не более одного активного таймера» (счётчик инстансов в DI). Или просто принять, что HMR-патч 4-1 непроверяем юнитом — тогда явно записать в спеку «HMR-dispose = ручная дисциплина, тестом не покрыта». Честнее первое.

**УСИЛЕНИЕ ④:** старт-после-Promise.all (удар 4-2) заодно убирает гонку «первый кадр до ready» для ЛЮБОГО будущего контура-D — дёшево сейчас, бесплатно потом.

**ВЕРДИКТ ④: ТРЕБУЕТ ПАТЧА** — держит при условии: HMR-dispose + старт после готовности контуров + PS-2 на повторный create/destroy.

**УСИЛЕНИЕ ⑤:** PV-2-двойной-ассерт (удар 5-1) — превращает «хрупкий» тест в самодоказательный: даже при дрейфе мока тест падает с ПОНЯТНОЙ причиной (A перестал врать), а не с загадочной.

## §6. АТАКА ⑥ — три 🔴 решения Боссу

**УДАР 6-1 (решение 1 — победа C расщепляет прод на два детектора):** правило пака §2 [У5] + проводка C при победе = замена в `_passiveTick` (`pitch-engine.ts:208`) + «yin-processor.js-близнец — вне скоупа [У8]» (спека ⑥-1). Следствие в реальном прогоне: vocal-нота считается C, mic-нота — старым A-worklet (`yin-processor.js`, со своей no_pitch-семантикой §4-Н1 и своим octLock `:176-183`). На PianoKeyboard (`PitchTab.tsx:378`) обе ноты рядом + isMatch-логика (`PitchTab.tsx:373`): на октавной ловушке mic покажет /2, vocal — нет → «✓ match» мигает/ломается на ровном месте, юзер видит рассинхрон клавиатуры. Это не гипотеза — это прямое следствие «C в vocal, A в mic». **Ловится:** первый же смоук после проводки C: юзер с включённым mic поёт в октавной ловушке. → **Патч-условие к решению 1:** победа C ⇒ микропак проводки ОБЯЗАН включать либо (а) worklet-близнец C, либо (б) явный feature-гейт «mic остаётся на A до синхронизации» + скрытие isMatch при детектор-миксе. «Вне скоупа [У8]» допустимо для СКОУПА стенда, но решение 1 не должно продаваться Боссу без этого условия — иначе вердикт «C дефолт» тихо создаёт двухголовый прод.

**УДАР 6-2 (решение 2 — смоук-неделя без критерия отката):** «DEV-флаг на неделю смоука» — но не определено, ЧТО считается провалом смоука. Редкий артефакт на тембре Никиты (1 раз/день) не будет замечен без формального чек-листа; после недели «тишины» C уходит в прод, юзеры с похожим тембром ловят артефакт первыми. **Ловится:** любой редкий C-артефакт на живом голосе (стемы ≠ живой mic: proximity/комната/дыхание). → **Патч-условие:** смоук-неделя = чек-лист сценариев (гроул, фальцет, бас, вибрато, шёпот) + критерий отката «любый live-брек C (аналог brokeByC на слух/записи) → A без обсуждения». Ноль кода, протокол.

**УДАР 6-3 (решение 3 — FFT-путь плодит третий YIN):** FFT-difference-спека (zero-pad 2N−1, кэш планов, running-sum) = третье CMND-ядро в кодовой базе (yin-detect, pyin-vote, fft-yin). Дрейф-риск ×3 при уже существующем прецеденте расхождения (§4-Н1: yin-detect vs yin-processor разошлись в живом дереве). **Ловится:** любой фикс edge-case в одном ядре после появления двух других — класс уже реализовался. → **Патч-условие:** FFT-спека обязана с рождения включать инвариант-тест «FFT-CMND ≡ direct-CMND» (тот же PV-6-механизм из §2, допуск float-погрешности FFT ~1e-6). Исследование без инварианта = третий источник правды.

**УСИЛЕНИЕ ⑥:** к решению 1 — тай-брейкер-формулировка упрощается: вычеркнуть слово «ничья» (при конъюнкции «C≥A+2пп бас/гроул И C≥A−1пп чистый» ничья почти недостижима и только запутывает); правило = чистая конъюнкция, иначе A. Меньше слов — меньше споров при чтении вердикта.

**ВЕРДИКТ ⑥: ТРЕБУЕТ ПАТЧА** — все три решения держат при условиях: (1) worklet-условие/гейт при победе C; (2) чек-лист + критерий отката смоука; (3) FFT-инвариант в спеке X.
