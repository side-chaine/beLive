## УДАРЫ

### УДАР 1: Геттер строится на условной инфраструктуре vocalHall — тап мертворождён без Router
**Сценарий:** HPS:220 `if (stemId === 'vocals' && this._vocalHallTarget)` — `_vocalHallSource` присваивается ТОЛЬКО при живом `_vocalHallTarget`. Цель ставится единственным местом — main.tsx:159, и только внутри `if (router)` (:157), а router = null при падении `new MonitorRouter(ctx)` (catch :116 — сценарий заложен в код).
**Следствие:** Router упал → `_vocalHallSource` НИКОГДА не присваивается → `vocalReferenceTap` = null на ВСЕХ треках при живом вокал-стеме. Деградация тихая: UI-чип «—» неотличим от «трек без вокала», диагностика нулевая (нет ни ошибки, ни лога). Флагман отключается целиком из-за падения МОНИТОРНОГО узла, к питч-референсу отношения не имеющего.
**Правка:** В loadStem:220-226 разделить присвоение и connect: `if (stemId === 'vocals') { this._vocalHallSource = instance.outputNode }` — безусловно; connect к `_vocalHallSend` (строки :221-225) — оставить под `this._vocalHallTarget`-условием. Геттер читает только `_vocalHallSource`, зал не задет, тап жив при любом router.

### УДАР 2: Смена трека — reset() сбрасывает тап, но НЕ рвёт ребро → чужой стем в зале (monitor-truth breach)
**Сценарий:** 001 добавляет `_vocalHallSource = null` в reset() (~:696). Но старый `instance.outputNode` остаётся ПОДКЛЮЧЁННЫМ к `_vocalHallSend` (:223 connect делался на loadStem прошлого трека). Пул НЕ диспоузит инстансы при reset — clearAllBuffers (Pool:257-270) чистит только маппинги; после reset все 7 слотов свободны и раздаются заново В ПОРЯДКЕ прихода стемов (Promise.all, недетерминирован). Слот, где был вокал трека A, при загрузке трека B может достаться ЛЮБОМУ стему (drums/other — их нет даже в STRETCH_PRIORITY → первые свободные).
**Следствие:** Старый outputNode (тот же физический узел!) теперь несёт гитару/ударники трека B → зомби-ребро `стем-B → _vocalHallSend → router.vocalHallInput` — **в зале (монитор педагога) играет гитара как «вокал»**. Проверка :222 (`if (this._vocalHallSource) disconnect`) уже не сработает — мы занулили поле. Откат 001 сам создаёт дыру R1, которую должен был лечить.
**Правка:** В reset() перед занулением: `if (this._vocalHallSource) { try { this._vocalHallSource.disconnect(this._vocalHallSend) } catch {} } this._vocalHallSource = null`. Две строки, рёбро честно разорвано, loadStem:221-225 дальше работает как задумано.

### УДАР 3: `ae?.isPlaying` в V3 = undefined → движок паузится ВСЕГДА; спасает только побочный IO-resume
**Сценарий:** Сверен живой рантайм: `js/audio-engine.js` НЕ грузится в index.html (:397-402 грузят только audio-facade-v3.js) → `window.audioEngine` = V3-фасад, а в фасаде НЕТ `isPlaying` (проверен весь объект: только getCurrentTime/play/pause/stop/stems-методы/audioContext/...). patchV1.ts, который defines isPlaying (:99-101), вызывается НУЛЕМ мест (grep: только определение). Значит PitchTab:260 `if (!ae?.isPlaying) eng.pause()` → `!undefined` = **true на каждом прогоне V3**.
**Следствие:** V3 auto-play (Interceptor:175) происходит ДО `track-fully-loaded` (:244), т.е. ДО tryInit → statechange 'playing' уже отгремел → resume из :274 НЕ придёт → после initFromNode движок уходит в pause и стоит до ручного pause/play пользователем. ФЛАГМАН МОЛЧИТ НА ПЕРВОМ ТРЕКЕ. Единственный спасатель — IntersectionObserver (:326-336, наблюдает #belive-react): его первый колбэк при видимом app зовёт resume ПОСЛЕ pause — случайное спасение, зависящее от порядка микрозадача-vs-IO-колбэк и видимости рут-элемента. Побочная мина: :347 `if (ae && !ae.isPlaying) return '⏸'` → ⏸ показывается при ЛЮБОЙ ненайденной ноте во время игры — UI-ложь «пауза».
**Правка:** PitchTab (зона прогона): обе читалки → store, который V3StatePublisher честно пишет (:113 `store.setPlaying`): в tryInit:260 `if (!useAudioStore.getState().isPlaying) eng.pause()`; в vocalDisplay — `const playing = useAudioStore(s => s.isPlaying)` и `if (!playing) return '⏸'`. Импорт audio.store — циклов нет (store не импортирует компоненты). 3 строки.

### УДАР 4: acquire-гонка — destroy во время in-flight acquire → стрим висит ВЕЧНО
**Сценарий (миниатюра «Удар-2а»):** MicSourceV3:33-47: `_refCount++` синхронно, потом `await _open()`; при провале catch:41-44 сам откатывает счётчик — внутри MicSourceV3 баланс идеальный. Но дизайн 001 (`this._stream = await micSource.acquire(); this._refNeeded = true`) ломается снаружи: студент ткнул 🎤, движение weборы разрешения затянулось, ткнул выкл → PitchTab-cleanup (:317-322) зовёт `eng.destroy()` → destroy видит `_refNeeded = false` (пока!) → release НЕ зовёт → continuation после резолва acquire выполняется ПОСЛЕ destroy: `this._stream = stream; this._refNeeded = true` — зомби-присвоение на брошенном движке (refs очищены, вызывать release некому).
**Следствие:** refcount MicSourceV3 = 1 навсегда → `release()` от будущих REC не доводит до 0 → стрим НИКОГДА не останавливается → индикатор захвата камеры/микрофона висит до перезагрузки страницы. Прямое нарушение инварианта 82e1c76, который slice и обещал закрыть.
**Правка:** В initFromMic после await: `const stream = await micSource.acquire(); if (this._status !== 'starting') { try { micSource.release() } catch {} return } this._stream = stream; this._refNeeded = true`. destroy ставит status='idle' (:252) → гард ловит и poison-destroy, и повторный init; release уравновешивает acquire в мёртвой ветке. `_refNeeded` ставить ТОЛЬКО после успешного await — иначе двойной decrement (acquire-catch уже откатил +1) съедает refcount чужого REC → стрим останавливается при живой записи.

### УДАР 5: tap null при живом движке → вокал-движок тикает в тишину
**Сценарий:** Смена трека на трек без вокала: tryInit → `if (!tap) return false` (патч 001) — но `vocalEngineRef.current` жив и running на СТАРОМ узле (после reset он молчит — буферы очищены), 46ms-тик жжёт CPU вхолостую до конца сессии таба.
**Следствие:** фоновый таймер-зомби + при следующем треке С вокалом retarget (:248) спасает, но между сменами — бесполезный тик. Не убийца, но халатность: `hasVocals=false` уже выставлен, движок должен спать.
**Правка:** В tryInit перед `return false`: `vocalEngineRef.current?.pause()`. Одна строка, resume вернёт playback-state-changed (:274).
