## ПРОМПТ (копируй в модель-дизайнер целиком, от ⬇️ до ⬆️)

⬇️

Спроектируй интерактивный **«Город» — визуальное зеркало программного репозитория** для вокальной браузерной платформы beLive. Это отдельный режим приложения, открываемый кнопкой: каждый пользователь нажимает — и видит город, где **каждое здание = режим платформы, каждый этаж = файл/модуль репозитория, каждый объект = сущность кода**. Город полностью зеркалит репозиторий и обновляется вместе с ним.

### ЧТО УЖЕ ЕСТЬ (прототип, нельзя потерять)
- Рендер v0.4.0: сетка 15×14, 9 районов, 17 зданий-режимов (B01–B17), 14 линий метро = реальные события шины, тёмные этажи = резервные слоты, снесённые этажи помечены [cleared]
- Кадастр houses.yaml: 74 объекта, формула «объект = этаж, здание = режим»; метрики churn×loc (горячие цеха = где чаще всего правят код)
- Подсветка зданий по активному режиму (rehearsal/karaoke/concert/live), инспектор здания с гейтами
- Печать владельца: «кайф, 9/10»

### ФУНКЦИОНАЛЬНЫЕ ТРЕБОВАНИЯ
1. **Кнопка «Город» в приложении** — вход из любого режима, полный экран
2. **Zoom-глубина с честной иерархией (4 уровня):** район → дом (статус+гейт) → этаж (файл, живость, метрики) → комната (функции/маркеры). На каждом уровне — только измеримые факты, никаких выдуманных деталей
3. **Стройка/оптимизация — видимые индикаторы:** на доме/этаже обозначается «в работе» (активная волна), «перегрет» (hotspot), «зарезервировано», «снесено честно», «спит» (осознанная пауза со сроком)
4. **Система обновления — из существующих потоков, не переизобретать:** город пересобирается из машиночных данных (кадастр+гейты+метрики+события) одной командой; визуал никогда не «знает» статус сам — его кормят данные
5. **Кликабельность:** дом → карточка (что за режим, какие этажи, гейты, статусы) → клик по этажу → файл/инструменты. Каждый элемент имеет двух-местный стык: дом ↔ файлы ↔ проверяющий гейт. Что не имеет стыка — не показывается

### ПРИНЦИПЫ (нарушать нельзя)
1. **Двухмашинная правда:** город показывает только то, что подтверждено измерением (кадастр + гейт/граф), а не «статус из декларации»
2. **Слои отделены от вида:** кадастровая модель (yaml/json) — отдельно от рендера (HTML/Canvas/WebGL). Дизайн рендера можно менять без потери данных
3. **Цвет = данные, не декор:** каждый цвет кодирует свойство (живость/перегрев/опасность/резерв); никаких градиентов «для красоты» там, где есть данные
4. **Анти-дальтонизм:** статус-цвета дублируются формой/паттерном (цвет + штриховка/иконка)
5. **Тёмный фон — математика, не глаз:** контраст текста ≥4.5:1, маркеров ≥3:1 к фону #05070D; «яркий» на тёмном умирает нелинейно — нормируй в OKLCH

### ЦВЕТОВАЯ СИСТЕМА (готовая рампа, пережившая 9/10)
- Amber-рампа живости (монотонная по светлоте в OKLCH): live → liveHot → liveDeep
- Frost-акцент #B2DFF4 — «иней» на резервах (единственный холодный)
- Hazard #E85433 — опасность/красное
- ⚠️ НЕ импортировать бренд-пару приложения #38A8FF/#FF5B5B без семантической роли — в городе они не значат то же, что в студии
- Зум-адаптивный бюджет: вид города = 4-5 цветов (массовое чтение), вид этажа = расширенная палитра

### ФИЧИ-КАНДИДАТЫ (сюрпризы, приветствуются)
- **«Дышащий город»:** перегретые цеха пульсируют свечением с частотой ∝ перегреву — город живёт в ритме реальной работы кода
- Режимы-свет: активный режим платформы подсвечивает свой квартал
- Метро-линии = живые события (едущие сигналы?)

### АНТИ-ТРЕБОВАНИЯ (что НЕ нужно)
- 3D-фотореализм, изометрия ради тренда, шум мелких деталей при глубоком зуме
- Статусы «из промпта» — модель рисует, но не знает; у каждого визуального элемента обязан быть якорь в данных
- Отдельная «админка» города — всё управление из тех же данных репозитория

### ФОРМАТ ОТВЕТА, КОТОРЫЙ ЖДУ ОТ ТЕБЯ (модель-дизайнера)
1. Концепт-картина словами (максимум 200 слов): как выглядит город на каждом из 4 уровней зума
2. Макет главного вида (описание композиции: сетка, ракурсы, плотность)
3. Таблица «элемент → цвет/форма → кодируемое свойство → источник данных»
4. Токен-лист: цвета/типографика/отступы с числами
5. Динамика: что анимируется, с какой частотой, что статично
6. Риски твоего дизайна и как их проверит программист (2-3 пункта)
